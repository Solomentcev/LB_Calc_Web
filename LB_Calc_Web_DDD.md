# Доменная модель LB_Calc_Web

**Назначение документа:** описание фактически реализованной доменной модели приложения на ветке `refactor-main`.

**Статус:** описание текущей реализации. Согласованные, но ещё не реализованные правила отдельно отмечены в документе «Бизнес-логика LB_Calc_Web».

> Документ отражает код, а не целевую архитектуру. Наличие класса в доменном пакете само по себе не означает, что все операции приложения уже выполняются через него.

## 1. Назначение предметной области

LB_Calc_Web предназначен для проектирования автоматизированных камер хранения (АКХ), формирования их конфигураций, расчёта геометрических параметров и подготовки представления конструкции.

Основные понятия предметной области:

- **Проект** — набор конфигураций АКХ, включённых в проект, с количеством каждой конфигурации.
- **ALS** — конфигурация автоматизированной системы хранения, состоящая из модулей в физическом порядке слева направо.
- **Модуль** — конструктивная часть ALS. В модели представлены модули хранения LB, управления LC и комбинированный LBC.
- **Ячейка хранения** — элемент модуля хранения, для которого рассчитываются размеры и назначается номер в составе ALS.
- **Конфигурация управления** — набор функций управления, способов доступа, вариантов печати и оборудования.
- **Оборудование** — устройства, используемые в конфигурациях модулей.
- **Сотрудник** — доменное представление сотрудника приложения с персональными данными и ролью.

## 2. Границы доменной модели

Основные доменные классы находятся в пакете:

`com.lb_calc_web.domain`

В модели выделены следующие группы:

| Группа | Основные типы | Назначение |
|---|---|---|
| Модели | `Project`, `ALS`, `Module`, `LB`, `LC`, `LBC`, `Employee` | Представление предметных объектов и их поведения |
| Конструктивные модели | `StorageModule`, `StorageCell`, `ControlModule` | Общая логика модулей хранения и управления |
| Конфигурации | `ControlConfiguration`, `EquipmentConfiguration` | Параметры функций управления и состав оборудования |
| Оборудование | `Equipment`, специализированные типы оборудования | Представление устройств |
| Атрибуты | `Colors`, `TypeLb`, `Payment`, `AccessMethod`, `PrintOption`, `DirectionDoorOpening`, `PositionControlModule`, `Role` | Значения и характеристики предметной области |

Доменная модель не содержит JPA-аннотаций и не обращается напрямую к Spring Data Repository. Идентификаторы БД и преобразования между доменом, DTO и JPA-сущностями находятся за пределами доменных объектов.

## 3. Доменная модель

### 3.1. Project

`Project` представляет проект и управляет его составом.

Основные атрибуты:

- `name` — название;
- `description` — автоматически формируемое описание состава;
- `company` — компания;
- `createdAt`, `updatedAt` — даты создания и изменения;
- `createdBy`, `updatedBy` — сотрудники;
- `quantityALS` — карта конфигураций ALS и их количества.

Состав хранится в виде `Map<ALS, Integer>`. Одна запись карты означает одну конфигурацию ALS и количество её экземпляров в проекте. Это доменное представление не содержит отдельного объекта для каждой физической копии одинаковой конфигурации.

Основные операции:

- `addALS(ALS)` — добавить одну единицу; если равная конфигурация уже есть, увеличить её количество;
- `removeALS(ALS)` — удалить одну единицу; при достижении нуля удалить конфигурацию из состава;
- `replaceALS(oldALS, newALS)` — заменить конфигурацию с переносом всего её текущего количества;
- `getQuantity(ALS)` — получить количество;
- `restore(...)` — восстановить проект из сохранённых данных без регистрации восстановления как нового изменения.

Изменение состава обновляет дату изменения и автоматически пересчитывает описание. `getQuantityALS()` возвращает карту только для чтения.

**Важное ограничение текущей реализации:** `replaceALS()` переносит всё количество старой конфигурации, а не одну единицу. Поэтому этот метод не реализует согласованное правило редактирования одного экземпляра ALS.

**Технический риск:** ALS используется как ключ изменяемой карты. При этом `ALS.equals()` и `hashCode()` зависят от конфигурации модулей, а сама ALS и её модули могут пересчитываться и изменяться. Изменение ключа после помещения в HashMap/LinkedHashMap может нарушить корректность поиска по ключу. Это зафиксированное ограничение реализации, а не допустимое бизнес-правило.

### 3.2. ALS

`ALS` — агрегат конструкции, объединяющий модули в физическом порядке слева направо.

Основные атрибуты:

- автоматически формируемые `name` и `description`;
- `height`, `width`, `depth`;
- `upperFrame`, `bottomFrame`;
- `colorBody`, `colorDoor`;
- упорядоченный список `modules`.

Список модулей — единственный источник истины для физического порядка. Положение модуля управления, направления открытия дверей, нумерация ячеек и общая ширина являются производными характеристиками.

Структурные инварианты:

1. В ALS должен находиться ровно один объект, реализующий `ControlModule`.
2. В ALS должен находиться хотя бы один объект, реализующий `StorageModule`.
3. Один объект LBC может одновременно выполнять роли `ControlModule` и `StorageModule`.
4. Порядок элементов списка определяет расположение модулей слева направо.

Основные операции:

- добавление модуля в конец или в указанную позицию;
- удаление конкретного экземпляра модуля по идентичности объекта;
- получение управляющего модуля и списка модулей хранения;
- получение общего количества ячеек;
- определение положения управляющего модуля;
- полный пересчёт производных характеристик.

Удаление модуля выполняется по идентичности (`==`), а не по `equals()`. Это позволяет различать два отдельных экземпляра одинаковой конфигурации модуля.

### 3.3. Module

`Module` — абстрактная базовая модель модуля.

Общие характеристики:

- название и описание;
- высота, ширина и глубина;
- размеры верхней и нижней рам;
- цвет корпуса и дверей.

Каждый конкретный модуль реализует `recalculate()`, пересчитывающий его производные параметры.

### 3.4. StorageModule и StorageCell

`StorageModule` — базовый класс модулей, содержащих ячейки хранения. Он хранит:

- конструктивный тип `TypeLb`;
- направление открытия дверей;
- список `StorageCell`;
- рассчитанные высоту, ширину и глубину ячейки;
- толщину дверцы, используемую при расчёте глубины.

Количество ячеек определяется размером списка объектов `StorageCell`, а не отдельным независимым счётчиком. Вызов `setCountCells()` создаёт новый список ячеек заданного размера и запускает пересчёт; отдельная идентичность/ID ячейки в доменной модели отсутствует. Номер ячейки назначается позднее агрегатом ALS.

Номера ячеек не являются частью самостоятельной конфигурации модуля. Их назначает ALS с учётом положения модуля в общей конструкции.

Размеры ячейки рассчитываются в `StorageModule`:

- ширина ячейки = ширина модуля − `TypeLb.deltaWidth`.

Поле `TypeLb.serviceZoneWidth` присутствует в конструктивном типе, но в текущем расчёте ширины ячейки не используется. Это расхождение с целевой формулой из ТЗ, где сервисная зона дополнительно вычитается из ширины модуля.
- глубина ячейки = глубина модуля − толщина дверцы;
- полезная высота = высота модуля − верхняя рама − нижняя рама − суммарная толщина полок между ячейками;
- высота ячейки = полезная высота / количество ячеек.

Результат высоты приводится к целому числу через приведение `double` к `int` (дробная часть отбрасывается, округление не выполняется). При нулевом количестве ячеек или отсутствии `TypeLb` пересчёт завершается исключением.

### 3.5. LB

`LB` — модуль хранения. Содержит конструктивные параметры, тип LB, направление открытия дверей и набор ячеек.

При пересчёте LB рассчитывает размеры ячеек, формирует наименование и описание. Сравнение конфигураций LB выполняется по исходным конструктивным параметрам; производные название, описание, размеры ячеек и номера ячеек не являются самостоятельными параметрами идентичности.

### 3.6. LC

`LC` — модуль управления. Он реализует интерфейс `ControlModule` и содержит конфигурацию управления и оборудование.

В конфигурации управления представлены способ оплаты, способы доступа, варианты печати и состав оборудования. LC не является модулем хранения и не содержит ячеек.

### 3.7. LBC

`LBC` — комбинированный модуль. Он совмещает функции модуля хранения и модуля управления, поэтому участвует в ALS одновременно как `StorageModule` и `ControlModule`.

Следствия:

- LBC учитывается как единственный модуль управления ALS;
- LBC также учитывается при подсчёте модулей хранения и ячеек;
- для направления открытия дверей LBC применяется отдельное правило, отличающееся от обычного LB.

### 3.8. ControlConfiguration

`ControlConfiguration` описывает функциональную конфигурацию управления:

- `Payment` — способ оплаты;
- `AccessMethod` — множество способов доступа;
- `PrintOption` — множество вариантов печати;
- `EquipmentConfiguration` — состав оборудования.

Способы доступа и варианты печати хранятся как множества: порядок их элементов не имеет предметного значения. При создании наборы копируются в независимые EnumSet, наружу возвращаются представления только для чтения.

### 3.9. EquipmentConfiguration

`EquipmentConfiguration` разделяет оборудование на обязательное и дополнительное.

Списки копируются при создании объекта. Доступ к ним предоставляется только для чтения; изменение выполняется доменными методами добавления и удаления. При сравнении конфигураций учитывается содержимое и порядок элементов списков.

### 3.10. Equipment

`Equipment` — базовая абстракция оборудования. В домене также представлены специализированные типы устройств, например дисплей, принтер, RFID-считыватель и считыватель штрихкодов.

Конкретные характеристики зависят от типа оборудования. Не следует трактовать базовый класс как утверждение, что все устройства имеют одинаковый набор характеристик.

### 3.11. Employee и Role

`Employee` — доменная модель сотрудника приложения. В ней представлены только предметные данные:

- `firstName` — имя;
- `lastName` — фамилия;
- `email` — адрес электронной почты;
- `registrationDate` — дата регистрации;
- `role` — роль сотрудника.

Конструктор требует ненулевые значения всех пяти атрибутов. Изменение доменного состояния явно представлено методом `changeRole(Role)`. Отдельных доменных методов изменения имени, фамилии или email в текущей модели нет. `Employee` не переопределяет `equals()` и `hashCode()`, поэтому сравнение экземпляров выполняется по ссылочной идентичности. Отдельного доменного класса `User` в текущей модели нет: сохранённая `EmployeeEntity` одновременно содержит данные сотрудника и учётные данные для входа.

`Role` содержит два значения:

- `ROLE_ADMIN` — административная роль;
- `ROLE_MANAGER` — роль менеджера.

Роль — доменный атрибут сотрудника, но фактические полномочия определяются не одним enum, а конфигурацией Spring Security и ограничениями контроллеров.

**Граница доменной модели:** `Employee` не содержит persistence ID, пароль/хэш пароля, JWT, признак активности или блокировки. Эти данные находятся в `EmployeeEntity` и security-слое. `EmployeeEntityMapper` намеренно не переносит ID и хэш пароля при преобразовании в домен и обратно.

### 3.12. Значения и конструктивные атрибуты

В предметной модели используются следующие типы значений:

| Тип | Представленные значения / данные | Назначение |
|---|---|---|
| `Payment` | `NONE`, `CASHLESS`, `CASH_AND_CARDS` | Вариант оплаты |
| `AccessMethod` | `PIN`, `QR_CODE`, `BARCODE`, `RFID` | Способы доступа |
| `PrintOption` | `PIN`, `QR_CODE`, `BARCODE` | Варианты печати |
| `DirectionDoorOpening` | `LEFT`, `RIGHT` | Направление открытия дверей |
| `PositionControlModule` | `LEFT`, `CENTER`, `RIGHT` | Положение управляющего модуля |
| `Colors` | Black, Blue, Cyan, DarkGray, Gray, Green, LightGray, Magenta, Orange, Pink, Red, White, Yellow | Цвет корпуса и дверей |
| `TypeLb` | Наименование типа, добавочная ширина, толщина полки, ширина сервисной зоны | Конструктивные параметры модуля хранения |

`TypeLb` — не enum, а отдельный неизменяемый объект со значениями `type`, `deltaWidth`, `shelfThick` и `serviceZoneWidth`. Его конструктор запрещает пустое наименование и отрицательные размеры. Равенство определяется всеми четырьмя полями. Значения могут поступать из конфигурации приложения.

В коде также присутствует `PositionLC` с теми же значениями положения. Наличие этого enum само по себе не доказывает, что он используется как отдельное бизнес-понятие: фактическое применение следует определять по конкретным местам использования.

### 3.13. Модель оборудования

Базовый `Equipment` задаёт название и контракт получения ширины, высоты, глубины и описания. Название обязательно и не может быть пустым.

Равенство оборудования реализовано финальными `equals()` и `hashCode()` по точному классу и названию. Следовательно, два объекта разных классов с одинаковым названием не равны, а два объекта одного класса с одинаковым названием считаются равными.

В текущем домене представлены:

- `Display`: варианты `NONE`, `LC10`, `LC17`, `LC19`; для них заданы размеры дисплея и минимальная ширина модуля;
- `Printer`: принтер;
- `RfidReader`: RFID-считыватель;
- `BarReader`: варианты `NONE`, `READER_1D`, `READER_2D`.

Для принтера, RFID-считывателя и сканеров текущие реализации возвращают нулевые габариты. Это характеристика имеющейся модели, а не утверждение об отсутствии физических размеров устройств.

В JPA-модели отдельная универсальная сущность каталога оборудования не подтверждена. Поэтому доменные типы оборудования нельзя автоматически трактовать как управляемый CRUD-каталог с отдельными записями и идентификаторами.

### 3.14. Состав конфигурации управления и оборудования

`ControlConfiguration` объединяет один вариант оплаты, множество способов доступа, множество вариантов печати и `EquipmentConfiguration`.

Для множеств способов доступа и печати:

- порядок элементов не имеет значения;
- при создании формируются независимые `EnumSet`;
- наружу возвращаются представления только для чтения.

`EquipmentConfiguration` разделяет оборудование на два упорядоченных списка: обязательное и дополнительное. При создании списки копируются, наружу выдаются только для чтения. Изменение выполняется методами добавления и удаления. При сравнении конфигураций учитываются содержимое и порядок элементов списков.

Само наличие обязательного и дополнительного списков не определяет алгоритм подбора, совместимости или размещения оборудования. Такие правила должны описываться отдельно только в той мере, в какой они подтверждены фактической реализацией.



**Особенности пересчёта конкретных модулей:**

- `LB.recalculate()` пересчитывает ячейки и формирует производные имя/описание модуля хранения.
- `LC.recalculate()` проверяет, что ширина LC не меньше максимальной ширины, требуемой установленным оборудованием, затем формирует имя и описание. Для дисплея требуемая ширина берётся из `Display.getWidth()`, который возвращает минимальную ширину модуля.
- `LBC.recalculate()` пересчитывает ячейки хранения и формирует производные имя/описание комбинированного модуля. В нём одновременно присутствуют storage- и control-конфигурации.
- `getEquipmentHeight()` у LC и LBC возвращает максимальную высоту среди установленного оборудования либо 0, если оборудование отсутствует.

## 4. Пересчёт ALS

Метод `ALS.recalculate()` выполняет последовательность:

1. Проверяет структурные инварианты ALS.
2. Передаёт общие параметры ALS всем модулям: высоту, глубину, размеры рам и цвета.
3. Рассчитывает направления открытия дверей модулей хранения с учётом положения управляющего модуля.
4. Вызывает пересчёт каждого модуля.
5. Перенумеровывает ячейки в порядке обхода модулей.
6. Рассчитывает общую ширину как сумму ширин модулей.
7. Обновляет наименование и описание ALS.

Положение управляющего модуля определяется индексом control-модуля в списке:

- индекс 0 — LEFT;
- последний индекс — RIGHT;
- промежуточный индекс — CENTER;
- ALS из одного LBC рассматривается как CENTER.

Для обычных модулей хранения направление открытия дверей определяется относительно положения control-модуля. Для LBC применяется отдельная ветвь правила.

## 5. Сравнение конфигураций

В доменной модели `equals()` используется для сравнения конфигураций модулей и ALS, а не для сравнения persistence-записей.

- ALS сравнивается по общим конструктивным параметрам и упорядоченному списку модулей.
- Порядок модулей имеет значение.
- Производные ширина, имя, описание и положение control-модуля отдельно не сравниваются.
- Модули сравниваются по исходным параметрам соответствующего типа.
- Для удаления конкретного модуля используется идентичность объекта, а не равенство конфигураций.

Поскольку часть сравниваемых объектов изменяема, применение доменных объектов в качестве ключей хеш-коллекций требует отдельного контроля жизненного цикла ключа.

## 6. Доменная модель и JPA-модель

Доменная модель не совпадает один к одному со структурой таблиц.

| JPA-сущность | Назначение |
|---|---|
| `ProjectEntity` | Сохранённый проект |
| `ProjectALSEntity` | Связь проекта с конфигурацией ALS и количество этой конфигурации |
| `ALSEntity` | Сохранённая конфигурация ALS |
| `ALSModuleEntity` | Связь ALS с модулем и его порядком |
| `ModuleEntity` | Сохранённая конфигурация модуля и её специализированные реализации |
| `EmployeeEntity` | Сохранённые данные сотрудника/учётной записи |

Ключевые различия:

- `ProjectALSEntity.id` — идентификатор связи, не идентификатор ALS.
- `ALSEntity.id` — идентификатор сохранённой конфигурации ALS.
- `ProjectALSEntity.quantity` — количество данной конфигурации в конкретном проекте.
- `ALSModuleEntity.id` — идентификатор связи модуля с ALS.
- `ModuleEntity.id` — идентификатор сохранённой конфигурации модуля.

Одна запись `ALSEntity` может быть связана с несколькими проектами через `ProjectALSEntity`. Поэтому изменение общей записи ALS затрагивает все проекты, ссылающиеся на неё.

Связь ALS с модулями организована через `ALSModuleEntity`. Порядок модулей хранится в связи. `ALSEntity` удаляет свои связи с модулями каскадно и через orphan removal; сама конфигурация `ModuleEntity` не является дочерней записью ALS и не должна удаляться только из-за удаления связи.

## 7. Повторное использование конфигураций

Сервисы модулей и ALS используют поиск совпадающих конфигураций перед созданием новой записи. Для модулей `ALSService.resolveModule()` сравнивает доменную конфигурацию с преобразованными из существующих `ModuleEntity` объектами и переиспользует найденную запись. При отсутствии совпадения создаётся новая.

Повторное использование сохранённой конфигурации не означает, что один изменяемый доменный экземпляр должен совместно использоваться несколькими независимыми операциями редактирования. Следует различать:
- повторное использование неизменяемой/неизменяемой в рамках операции записи конфигурации в хранилище;
- совместное использование изменяемого объекта в памяти;
- связь нескольких проектов с одной записью `ALSEntity`.

## 8. Границы реализации и механизмы, которые нельзя приписывать домену

В текущем коде не подтверждены как реализованные именно на доменном уровне:

- публикация доменных событий агрегатами `Project`, `ALS`, `Employee`;
- отдельные доменные сервисы для разрешения требований и распределения оборудования;
- универсальный агрегат оборудования с единым управляемым каталогом всех типов;
- полная неизменяемость ALS и модулей после сохранения;
- отдельный серверный Draft-агрегат ALS;
- гарантированная независимость редактируемой ALS от других проектов, использующих ту же запись `ALSEntity`.

При этом в приложении **реализована отдельная интеграция пользовательских событий через Kafka**: `AuthService` формирует `UserEvent` и отправляет его через `KafkaTemplate`, а отдельный `notification-service` содержит Kafka consumer. Это прикладная интеграция, инициируемая сервисом, а не механизм доменных событий внутри агрегатов.

Наличие интеграционных событий не означает, что все значения `UserEventType` уже публикуются или что фактически отправляется email: текущее состояние описано в документе «Бизнес-логика LB_Calc_Web».

## 4. Согласованные предметные правила и целевая семантика домена

Этот раздел фиксирует решения, согласованные при уточнении предметной области. Они имеют приоритет над прежними формулировками этого документа, если те описывают только текущее поведение кода. Фактические расхождения реализации отдельно перечислены в документе «Бизнес-логика LB_Calc_Web».

### 4.1. Проект и состав ALS

- Доменный `Project` представляет состав проекта через `Map<ALS, Integer> quantityALS`: ключ — конфигурация ALS, значение — количество одинаковых экземпляров.
- Равные конфигурации ALS в доменном составе агрегируются в одну запись с количеством. Порядок ALS в проекте не имеет предметного значения.
- DTO может представлять состав физическим списком `alsList`; при преобразовании DTO в домен количество вычисляется по этому списку. `quantityALS` — доменное представление, а не отдельный источник данных DTO.
- В persistence количество хранится в связи проекта с ALS (`ProjectALSEntity.quantity`); идентификатор связи и идентификатор сохранённой ALS — разные идентификаторы.
- Редактирование одной выбранной ALS в составе проекта изменяет ровно один экземпляр. Если в проекте три одинаковых ALS, изменение одной конфигурации должно оставить две исходные и добавить одну новую конфигурацию. Другие проекты, использующие исходную конфигурацию, не меняются.
- Массовое редактирование всех одинаковых экземпляров — отдельный сценарий, не поведение по умолчанию.
- Для изоляции редактируемого экземпляра прикладной сценарий должен получить выбранную ALS из контекста проекта, создать глубокую независимую копию, применить изменения и передать результат в Project. Равные неизменяемые конфигурации модулей могут переиспользоваться, если не разделяется изменяемое состояние.
- Порядок модулей внутри ALS имеет значение и задаёт физическое расположение слева направо. Порядок самих ALS в проекте значения не имеет.

### 4.2. Состав ALS и роли модулей

- `LB` — модуль хранения.
- `LC` — модуль управления.
- `LBC` — один физический комбинированный модуль, одновременно выполняющий роли хранения и управления. Он не трактуется как два отдельных модуля.
- ALS должна содержать ровно один управляющий модуль (`LC` или `LBC`) и хотя бы один модуль хранения (`LB` или `LBC`).
- Допустимые базовые композиции из ТЗ: `LC + LB`, `LB + LC`, `LB + LC + LB`, `LBC`, `LBC + LB`, `LB + LBC`, `LB + LBC + LB`.
- LBC засчитывается одновременно как единственный управляющий и как модуль хранения.
- Примеры описывают физический порядок слева направо; вставка/удаление модуля должна сохранять структурные инварианты ALS.

### 4.3. Оборудование и функциональность

- `EquipmentConfiguration` является частью конфигурации управления внутри `LC/LBC`. Фактически установленное оборудование не хранится как отдельная часть ALS.
- Функциональные возможности ALS не сохраняются как самостоятельная конфигурация: они определяются характеристиками и моделями оборудования, а также значениями конфигурации управления.
- `FunctionalSelection`, если используется на прикладном/UI-уровне, представляет временное состояние выбора и не является сохраняемой частью конфигурации.
- Для LC и LBC согласовано единое правило разрешения требований к оборудованию через целевой общий `EquipmentRequirementResolver`. Наличие полноценного resolver в текущей реализации не подтверждено.
- Доменная модель не должна вызывать сервисы, репозитории или обращаться к persistence. Координация проекта и выбранной ALS относится к `ProjectService`; управление составом/порядком модулей — к ответственности ALS; собственные параметры конфигурации — к соответствующим моделям модулей.

### 4.4. Неизменяемость и идентичность конфигураций

- Целевой принцип: сохранённые конфигурации оборудования, модулей и ALS не редактируются на месте. Изменение приводит к поиску полностью равной конфигурации или созданию новой (Find-or-Create).
- Идентичность ALS включает её характеристики и упорядоченный список модулей; перестановка модулей означает другую конфигурацию.
- Производные значения — название, описание, рассчитанные размеры ячеек, номера ячеек и иные вычисляемые характеристики — сами по себе не являются параметрами идентичности.
- Согласно ТЗ, идентичность Equipment определяется типом, производителем, моделью, техническими характеристиками и габаритами; ID, цена, активность и признак default в неё не входят.
- В ТЗ остаётся противоречие: состав оборудования модуля в одном месте задаётся бизнес-идентичностью Equipment, а в другом — парами `(equipmentId, quantity)`. До отдельного согласования нельзя считать это противоречие разрешённым.
- Жизненный цикл конфигурации, заданный ТЗ: DRAFT → SAVED/IMMUTABLE → USED → ORPHAN; архивация выполняется администратором. Архивирование не тождественно физическому удалению.
- Полная неизменяемость и весь жизненный цикл пока не обеспечены реализацией.

### 4.5. Геометрия и общие параметры ALS

- Высота, глубина, верхняя/нижняя рамы и цвета корпуса/дверей являются общими параметрами ALS и синхронизируются с её модулями.
- Ширина ALS — сумма ширин модулей в физическом порядке.
- Формулы предметного расчёта:
  - ширина ячейки = ширина модуля − `deltaWidth` − `serviceZoneWidth`;
  - глубина ячейки = глубина модуля − толщина дверцы;
  - полезная высота = высота модуля − верхняя рама − нижняя рама − (`countCells - 1`) × толщина полки;
  - высота ячейки = полезная высота / количество ячеек.
- Высота ячейки округляется вниз отбрасыванием дробной части, а не математическим округлением.
- Верхняя/нижняя рамы, высота, глубина, ширина, тип LB, толщина дверцы и количество ячеек имеют ограничения и значения по умолчанию; полный перечень и динамические зависимости приведены в документе «Бизнес-логика LB_Calc_Web».
- Ограничение `countCells <= 20` — только абсолютный верхний предел. Реально допустимое количество зависит от полезной высоты, минимальной высоты ячейки и толщины полки.
- Текущая реализация ширины ячейки вычитает только `deltaWidth`; `serviceZoneWidth` в расчёте не участвует. Это известное расхождение с формулой ТЗ, а не изменение согласованной формулы.

### 4.6. Положение управляющего модуля

- Для ALS с отдельным LC положение управляющего модуля определяется его индексом в упорядоченном списке и соответствует LEFT, CENTER или RIGHT.
- Положение является производной характеристикой, а не независимым источником физического порядка.
- Для ALS, состоящей из единственного LBC, физическое положение управляющего модуля LEFT/CENTER/RIGHT неприменимо: LBC одновременно занимает всю конструкцию.
- Техническое представление этого исключения (отдельное значение SINGLE либо отсутствие/неприменимость позиции) остаётся открытым вопросом. Значение CENTER по умолчанию из properties не превращает одиночный LBC в физически центральный модуль.

### 4.7. Сотрудники, учётные записи и доступ

- `Employee` — доменная модель сотрудника; пароль, его хэш, JWT и security principal не относятся к доменному объекту.
- `EmployeeEntity` в текущей реализации объединяет данные сотрудника и учётные данные. Отдельной доменной сущности `UserAccount` пока нет; необходимость её выделения не решена.
- Роль сотрудника относится к доменной модели. Реальные полномочия дополнительно обеспечиваются security/application-слоем.
- По ТЗ менеджер видит все проекты, но редактирует только собственные; администратор может редактировать любые проекты. Проверка принадлежности проекта сотруднику в текущей реализации отсутствует.
- Политика удаления/деактивации сотрудника, на которого ссылаются проекты как на автора или редактора, остаётся открытой.

### 4.8. Гостевой режим

- Гостевые проекты хранятся локально в IndexedDB браузера; серверная БД не хранит гостевые проекты и не создаёт для них гостевые учётные записи.
- Гостевой режим использует те же доменные правила расчёта и проверки, что и авторизованный режим.
- После регистрации/входа пользователь выбирает проекты для импорта. Сервер повторно валидирует данные и назначает владельца по аутентифицированному principal, а не по переданному клиентом идентификатору.
- Локальный проект удаляется только после подтверждения успешного сохранения на сервере. Неуспешные и необработанные проекты остаются в IndexedDB.
- Идемпотентность повторной отправки, политика конфликтов/дубликатов и точный протокол повторной попытки остаются открытыми техническими деталями.
- Сквозная реализация IndexedDB и импорта в текущем приложении не подтверждена.
