# Бизнес-сценарии и состояние реализации LB_Calc_Web

**Назначение документа:** описать фактическое поведение бизнес-сценариев в коде, выявленные расхождения с целевыми требованиями и согласованные правила, ожидающие реализации.

**Область фактического анализа:** ветка `refactor-main`.

**Правило чтения:** разделы 1–12 описывают текущие сценарии и ограничения реализации; раздел 13 фиксирует согласованные целевые правила и открытые предметные вопросы. Целевое правило не является доказательством его реализации.

## 1. Принципы предметной логики

1. Проект содержит конфигурации ALS и количество каждой конфигурации.
2. ALS является упорядоченной конструкцией из модулей.
3. В ALS должен быть ровно один модуль управления и хотя бы один модуль хранения. LBC совмещает обе роли.
4. Геометрические параметры ячеек и ALS вычисляются из конструктивных параметров модулей.
5. Повторяющиеся конфигурации могут ссылаться на одну сохранённую запись конфигурации.
6. Идентификатор сохранённой конфигурации ALS не тождественен идентификатору её включения в проект.
7. Транзакция обеспечивает атомарность операций сохранения, но сама по себе не обеспечивает независимость общей конфигурации от изменений.

## 2. Управление проектом

### 2.1. Создание проекта

Текущий сценарий в `ProjectService`:

1. Получает сотрудника, выполняющего создание.
2. Формирует доменный `Project` с названием, компанией и датой создания.
3. Преобразует проект в `ProjectDTO`.
4. Инициализирует DTO идентификатором нового проекта и формирует название.
5. Для формы создания может дополнительно создать начальную конфигурацию ALS и включить её в список DTO.

Фактическое сохранение выполняется отдельным вызовом `saveProject()`.

### 2.2. Сохранение проекта

Текущая последовательность `ProjectService.saveProject(ProjectDTO)`:

1. Загружает существующий `ProjectEntity`, если передан положительный ID.
2. Получает текущего сотрудника и проверяет право изменения существующего проекта.
3. Устанавливает серверные метаданные: автора/дату создания берёт из БД, автора/дату изменения — из текущего контекста.
4. Преобразует DTO в доменный `Project` и выполняет глубокую проверку до сохранения конфигураций.
5. Сохраняет каждую ALS через `ALSService.saveALS()` по Find-or-Create; получает канонические DTO с persistence ID.
6. Повторно собирает доменный Project из канонических DTO.
7. Разрешает доменные ALS в `ALSEntity` по полученным ID.
8. Создаёт или обновляет `ProjectEntity`; при обновлении сохраняет существующие строки `ProjectALSEntity` и их ID, если ALS остаётся в составе проекта.
9. Сохраняет проект в рамках общей транзакции.

Доменный `Project` агрегирует равные конфигурации ALS в `Map<ALS, Integer>`. DTO при этом использует список элементов ALS и отдельное UI-представление количества. Следовательно, DTO, доменная модель и JPA-модель представляют состав проекта по-разному.

### 2.3. Добавление ALS

В `ProjectService.addNewALSandSaveProject()`:

1. Загружается проект.
2. Через `ALSService.createALS()` формируется DTO начальной конфигурации.
3. DTO добавляется в список проекта.
4. Проект сохраняется через `saveProject()`.

### 2.4. Удаление ALS

Текущий `deleteALSandSaveProject(projectId, alsId)`:

1. Загружает проект и находит выбранную ALS по persistence ID.
2. Восстанавливает доменный Project.
3. Вызывает `Project.removeALS()`, уменьшая количество выбранной конфигурации ровно на одну единицу.
4. Сохраняет изменённый состав через `saveProject()`.

Если количество конфигурации становится нулевым, связь Project–ALS удаляется. Сама `ALSEntity` не удаляется этим сценарием, поскольку может использоваться другими проектами.

### 2.5. Чтение, удаление и экспорт проекта

В `ProjectService` также реализованы операции:

- `findAll()` — получение списка проектов;
- `findById(id)` — получение проекта по идентификатору;
- `deleteById(id)` — удаление проекта;
- `exportToExcel(id)` — формирование Excel-представления проекта.

Экспорт выполняется через отдельный helper. Детали состава и формата экспортируемых листов следует описывать отдельно по реализации `ExcellHelper`; сам факт наличия метода не означает, что все виды спецификаций или отчётов поддерживаются.

### 2.6. Фактическое ограничение доступа к проектам

REST- и MVC-маршруты проектов требуют аутентификацию. Чтение проектов не ограничено владельцем: `ProjectService.findAll()` возвращает все проекты, а `findById()` загружает проект по ID. Это соответствует правилу, по которому менеджер видит все проекты.

Изменение и удаление проверяются в `ProjectService`. Администратор может изменять и удалять любой проект; менеджер — только проект, в котором он указан как `createdBy`. Проверка выполняется в `saveProject()` для всех сценариев изменения состава/конфигурации и в `deleteById()` для удаления. Метаданные владельца при обновлении берутся из БД, а не из DTO клиента.

## 3. Создание и сохранение ALS

### 3.1. Создание начальной конфигурации

`ALSService.createALS()` получает базовые размеры, размеры рам, цвета и положение управляющего модуля из конфигурации приложения. Затем создаёт DTO управляющего модуля LC и DTO модуля хранения LB, помещает их в ALSDTO, рассчитывает производные данные и формирует визуальное представление.

Этот метод формирует начальную конфигурацию для дальнейшего редактирования/сохранения; сам по себе он не означает создание сохранённой записи ALS в БД.

### 3.2. Сохранение ALS

Текущий `ALSService.saveALS(ALSDTO)` выполняет:

1. Преобразует входной DTO в доменную ALS, разрешая параметры TypeLb из конфигурации приложения.
2. Выполняет глубокую проверку размеров и структуры.
3. Ищет кандидатов ALS по базовым скалярным параметрам, затем сравнивает полные доменные конфигурации.
4. При полном совпадении возвращает существующую конфигурацию и её ID независимо от входного ID DTO.
5. Если совпадение не найдено, создаёт новую `ALSEntity`; каждый модуль разрешается через Find-or-Create и может переиспользовать только полностью равную конфигурацию.
6. Сохраняет новую ALS и возвращает DTO с фактическими ID.

Существующие `ALSEntity` и `ModuleEntity` не обновляются по входному ID. Изменённая конфигурация создаётся как новая запись; прежняя остаётся доступной другим проектам.

### 3.3. Общие сохранённые конфигурации

`ProjectALSEntity` ссылается на `ALSEntity` через ManyToOne. Это позволяет нескольким проектам использовать одну сохранённую конфигурацию ALS. Аналогично конфигурации модулей могут переиспользоваться разными связями ALS.

Это механизм повторного использования неизменяемых конфигураций. Изменение ALS выполняется созданием/поиском новой конфигурации и заменой количества в конкретном проекте; общая сохранённая запись не обновляется.

### 3.4. Работа с библиотекой ALS

В `ALSService` доступны операции чтения всех сохранённых конфигураций (`findAll`), получения одной конфигурации по ID (`findById`) и удаления сохранённой конфигурации (`deleteALS`). Удаление выполняется непосредственно по ID `ALSEntity`; отдельная бизнес-операция удаления ALS из конкретного проекта — другой сценарий и выполняется через `ProjectService`.

Конфигурация ALS в библиотеке и включение этой конфигурации в проект — разные операции. Связь проекта с ALS хранится отдельно и содержит количество. При этом одна `ALSEntity` может использоваться несколькими проектами, поэтому удаление/изменение записи библиотеки необходимо рассматривать с учётом всех ссылок на неё.

## 4. Редактирование модулей

### 4.1. Изменение LB

В текущем приложении операции над LB выполняются через `ProjectService`, `ALSService` и `LBService`. Сервисный сценарий изменяет параметры выбранного LB в DTO ALS, сохраняет модуль, затем сохраняет ALS и обновляет состав проекта.

Сохранение конфигурации модуля использует поиск совпадений: существующая равная конфигурация может быть переиспользована; при отсутствии совпадения создаётся новая запись.

### 4.2. Добавление и удаление LB

В `ALSService` доступны операции добавления и удаления LB с последующим пересчётом DTO ALS и сохранением ALS.

В текущих методах `addNewLBandSaveALS(alsId)` и `deleteLBandSaveALS(alsId, lbId)` ALS повторно загружается по глобальному ID. При использовании этих методов из сценария редактирования проекта важно удостовериться, что загруженная ALS является именно выбранным экземпляром в контексте проекта, а не общей конфигурацией, которую используют другие проекты.

### 4.3. Замена LC и LBC

Для замены управляющего модуля используются операции, которые устанавливают в ALSDTO новый LC либо LBC и очищают альтернативное поле управляющего модуля. Затем выполняется пересчёт DTO и сохранение ALS.

LBC при этом остаётся одним физическим модулем, совмещающим роли управления и хранения.

### 4.4. Фактические операции редактирования модулей в проекте

Сервисный слой содержит следующие сценарии:

| Операция | Текущая последовательность |
|---|---|
| `saveLBAtProject` | Загружает проект и ALS, проверяет наличие LB по ID, подменяет LB в DTO-списке, сохраняет ALS, затем заменяет ALS в проекте |
| `addLBAtProject` | Проверяет наличие ALS в проекте, вызывает `ALSService.addNewLBandSaveALS(alsId)`, затем сохраняет обновлённую ALS в проекте |
| `deleteLBatProject` | Проверяет наличие LB в контексте проекта, вызывает `ALSService.deleteLBandSaveALS(alsId, lbId)`, затем сохраняет обновлённую ALS в проекте |
| `saveLCAtProject` | Загружает проект и ALS, проверяет LC, сохраняет переданный LC с прежним ID через сценарий замены LC |
| `saveLBCAtProject` | Аналогично сохраняет LBC с прежним ID через сценарий замены LBC |
| `replaceLCandSaveProject` | Устанавливает LC, очищает поле LBC, пересчитывает и сохраняет ALS, затем заменяет ALS в проекте |
| `replaceLBCandSaveProject` | Устанавливает LBC, очищает поле LC, пересчитывает и сохраняет ALS, затем заменяет ALS в проекте |
| `replaceWithNewLBCAtProject` | Должен заменить управляющий модуль выбранной ALS новым LBC, но текущая реализация повторно загружает ALS по глобальному ID внутри `ALSService` |

В большинстве операций сначала выполняется проверка, что переданный ID найден внутри выбранного проекта и ALS. Однако сама последующая операция добавления/удаления LB или создания нового LBC повторно загружает ALS через `ALSService` по глобальному ID. Проверка контекста проекта не делает дальнейшую загрузку независимой копией.

При сохранении LB/LC/LBC передаваемому DTO присваивается ID редактируемого модуля. При сохранении ALS в проекте старый ID ALS также сохраняется в DTO. Поэтому это текущая модель обновления существующих записей, а не согласованный сценарий создания отдельной версии конфигурации для одного экземпляра проекта.

Для LC и LBC замена взаимоисключающая: при установке LC поле LBC очищается, при установке LBC поле LC очищается. В ALS после пересчёта должен оставаться один управляющий модуль.

### 4.5. Оборудование в текущей реализации

Каталог оборудования хранится в таблице `equipment_catalog`. Его JPA-модель — `EquipmentCatalogEntity`, доступ к данным выполняет `EquipmentCatalogRepository`, прикладные операции — `EquipmentCatalogService`. Схема и начальные позиции создаются миграциями Flyway V2–V4.

В каталоге сохраняются стабильный `catalog_position_id`, категория, название, описание, физические характеристики, поддерживаемые возможности, активность и признак модели по умолчанию. Начальные позиции сохраняют прежние ID: три дисплея, два сканера штрихкодов, принтер и RFID-считыватель. Миграция V4 задаёт модели по умолчанию для DISPLAY, BAR_READER, PRINTER и RFID_READER. Миграция V5 добавляла COMPUTER, LOCK_CONTROLLER, POWER_SUPPLY, UPS, PAYMENT_TERMINAL и CASH_ACCEPTOR. Историческая V6 временно деактивировала COMPUTER, POWER_SUPPLY и UPS; компенсирующая V7 восстанавливает их активность и признак модели по умолчанию (если для категории не назначена другая активная модель по умолчанию). Категории COMPUTER, LOCK_CONTROLLER, POWER_SUPPLY и UPS не управляются функциональным резолвером; существующие позиции сохраняются при пересчёте функциональности.

LC/LBC хранят состав оборудования в `lc_equipment` и `lbc_equipment` как `catalog_position_id + quantity`. Внешние ключи запрещают физическое удаление используемой позиции. Деактивация не удаляет модель и не мешает восстановить её в ранее сохранённой конфигурации.

В DTO добавлен список `equipmentSelections` с ID каталожной позиции и количеством. Если список не передан, мапперы сохраняют совместимость со старыми полями display/barReader/printer/rfidReader; если legacy-форма не передаёт количества, они выводятся из выбранной позиции или признака наличия оборудования. Формы LC и LBC, включая редактирование управляющего модуля внутри ALS, задают способы доступа через `accessMethods`; отдельные legacy-поля выбора принтера и считывателей в этих формах не используются. Значение доступа по умолчанию для LC и LBC — RFID; оно согласовано с legacy-признаком наличия RFID-считывателя. Главная форма редактирования ALS изменяет параметры агрегата, но не состав управляющего модуля: при сохранении существующей ALS LC/LBC восстанавливается из БД, чтобы не потерять полный каталог оборудования и функциональные настройки, редактируемые на отдельной форме модуля. Сервисный слой разрешает новые позиции только из активного каталога; при редактировании существующей конфигурации разрешает сохранить деактивированные позиции, уже входившие в её состав.

`EquipmentRequirementResolver` назначает оборудование только по функциональности LC/LBC. Базовая комплектация не формируется: категории LOCK_CONTROLLER, COMPUTER, POWER_SUPPLY и UPS не входят в управляемые категории и сохраняются при пересчёте как дополнительное оборудование. `CASH` требует CASH_ACCEPTOR; `CASHLESS` — PAYMENT_TERMINAL; `CASH_AND_CARDS` — PAYMENT_TERMINAL и CASH_ACCEPTOR. Выбранный монитор 10″/17″/19″ передаётся как выбранная каталожная позиция DISPLAY в `equipmentSelections`; отдельного поля монитора в доменной модели нет. Выбор дисплея сохраняется независимо от PIN. PIN без выбранного дисплея автоматически получает модель дисплея по умолчанию и требует дополнительный способ доступа RFID, BARCODE или QR. RFID, BARCODE и QR требуют совместимых считывателей. Принтер требуется при ненулевой оплате, BARCODE, QR или PIN; отдельный `PrintOption` не инициирует подбор принтера. Дополнительные категории не удаляются при пересчёте функциональности.

Для используемой позиции запрещено изменять категорию, название, габариты и характеристики совместимости: название участвует в формировании описания LC/LBC. Описание каталожной позиции может обновляться. Группы required/additional в БД не разделяются: сохраняется физический состав и количество, а не группа добавления.

## 5. Геометрические расчёты

### 5.1. Расчёт ячеек

Для storage-модуля используются:

- высота и глубина модуля;
- верхняя и нижняя рамы;
- количество ячеек;
- толщина полки из `TypeLb`;
- добавочная ширина из `TypeLb`;
- толщина дверцы.

Текущие формулы в `StorageModule`:

`cellWidth = moduleWidth - typeLb.deltaWidth - typeLb.serviceZoneWidth`

Ширина сервисной зоны участвует в расчёте как часть конструктивного типа.

`cellDepth = moduleDepth - doorThickness`

`usableHeight = moduleHeight - upperFrame - bottomFrame - (countCells - 1) * shelfThick`

`cellHeight = usableHeight / countCells`

Перед сохранением также выполняется проверка размеров средствами `SizeValidator`. Конкретные пределы должны сверяться с актуальным `size-bounds.properties` и реализацией валидатора; их не следует дублировать здесь как неизменные константы.

### 5.2. Пересчёт ALS

`ALS.recalculate()`:

1. проверяет наличие ровно одного управляющего и хотя бы одного storage-модуля;
2. синхронизирует общие конструктивные параметры ALS с модулями;
3. определяет направления открытия дверей;
4. пересчитывает каждый модуль;
5. перенумеровывает ячейки в порядке модулей;
6. суммирует ширину модулей;
7. формирует имя и описание ALS.

Порядок модулей имеет физический смысл и влияет на конфигурацию, направления дверей и нумерацию ячеек.

### 5.3. Ограничения размеров и глубокая валидация

Параметры по умолчанию и границы загружаются из `size-bounds.properties`. Линейные размеры задаются в миллиметрах.

| Параметр | Ограничение | Значение по умолчанию |
|---|---:|---:|
| Верхняя рама | 20–300 мм | 50 мм |
| Нижняя рама | 20–300 мм | 50 мм |
| Высота ALS/LB | 125–2300 мм | 1940 мм |
| Высота LC | минимум 600 мм, общий максимум 2300 мм | 1940 мм (общий default) |
| Высота ячейки | минимум 85 мм | — |
| Высота панели LC | минимум 300 мм | — |
| Глубина ALS/LB/LC | 170–900 мм | 500 мм |
| Глубина ячейки | 100–880 мм | — |
| Ширина модуля | 100–1200 мм | 500 мм |
| Ширина ячейки | минимум 100 мм | — |
| Количество ячеек | 1–20 | 3 |
| Толщина дверцы | 5–50 мм | 20 мм |
| `TypeLb.deltaWidth` | 0–500 мм | зависит от типа |
| `TypeLb.shelfThick` | 0–100 мм | зависит от типа |
| `TypeLb.serviceZoneWidth` | 0–300 мм | зависит от типа |

В конфигурации определены типы LB:

| Тип | Добавочная ширина | Толщина полки | Ширина сервисной зоны |
|---|---:|---:|---:|
| TYPE1 | 100 мм | 5 мм | 40 мм |
| TYPE2 | 100 мм | 20 мм | 40 мм |
| TYPE3 | 160 мм | 20 мм | 40 мм |
| TYPE4 | 60 мм | 5 мм | 0 мм |

Дополнительные значения по умолчанию:
- ALS: корпус Blue, двери White, положение управляющего модуля CENTER;
- LC: дисплей LC10, сканер штрихкода «Без сканера», оплата NONE, принтер выключен, RFID-считыватель включён, цвета Blue/White;
- LBC: TYPE1, дисплей LC10, сканер «Без сканера», оплата NONE, принтер выключен, RFID-считыватель включён, направление LEFT, цвета Blue/White.

**Важно:** приведённые значения — текущие настройки конфигурации. Фактическая допустимость отдельных значений зависит также от динамических проверок `SizeValidator`, а не только от простого сравнения с одной общей границей.

Глубокая проверка выполняется по уровням:

1. `validateALS()` проверяет габариты ALS и согласованность её конструктивных параметров.
2. `validateLC()` проверяет габариты и согласованность LC.
3. `validateLB()` проверяет рамы, тип LB, высоту, глубину, ширину, толщину дверцы, количество ячеек и рассчитанные размеры ячейки.
4. `validateLBC()` проверяет параметры хранения и управления комбинированного модуля, включая ограничение ширины по storage-параметрам и выбранному дисплею.
5. `deepValidateALS()` собирает результаты проверки ALS, управляющего модуля (LC либо LBC) и каждого LB.
6. `validateProject()` запускает глубокую проверку для каждой ALS в проекте.

Для LB и LBC минимальная высота модуля зависит от высоты рам и минимальной высоты ячейки. Максимально допустимое количество ячеек также ограничивается доступной высотой, толщиной полок и общим пределом 20 ячеек. Поэтому нельзя трактовать `countCells.max=20` как безусловное разрешение установить 20 ячеек при любой высоте модуля.

## 6. Сотрудники, учётные записи и роли

В приложении необходимо различать доменного сотрудника, сохранённую учётную запись и security-представление пользователя.

- `Employee` — доменная модель с именем, фамилией, email, датой регистрации и ролью.
- `EmployeeEntity` — JPA-сущность. Помимо доменных данных, содержит ID и хэш пароля.
- `EmployeePrincipal` — объект Spring Security, содержащий ID, email, хэш пароля и роль. Email используется как username, роль преобразуется в единственное полномочие с именем enum.
- `EmployeeDTO`, `ProfileDTO`, `RegistrationDTO`, `CreateEmployeeDTO` — транспортные модели для разных сценариев; они не являются доменными сущностями.

### 6.1. Роли и доступ

В enum `Role` определены:

- `ROLE_ADMIN`;
- `ROLE_MANAGER`.

Фактические ограничения доступа в текущей конфигурации:

| Область | Доступ |
|---|---|
| Регистрация и вход | Без аутентификации |
| REST login/registration/logout/refresh | Без аутентификации |
| Swagger и OpenAPI | Без аутентификации |
| `/employees/**` | Только `ROLE_ADMIN` |
| REST-контроллер `/api/v1/employees/**` | Только `ROLE_ADMIN` на уровне класса |
| Остальные запросы | Требуется аутентификация |
| Просмотр профилей через `/profiles` | Доступен аутентифицированному пользователю; отдельная проверка роли в контроллере не задана |

В `EmployeePrincipal` методы `isAccountNonExpired()`, `isAccountNonLocked()` и `isCredentialsNonExpired()` возвращают `true`. Метод `isEnabled()` отражает `EmployeeEntity.active`: деактивированная учётная запись не проходит вход и проверку Access/Refresh JWT. Отдельные механизмы блокировки и истечения срока действия учётной записи не реализованы.

### 6.2. Самостоятельная регистрация

Сценарий `AuthService.registration()`:

1. Проверяет совпадение пароля и подтверждения.
2. Проверяет, что email ещё не зарегистрирован.
3. Создаёт доменного сотрудника с датой `LocalDate.now()` и ролью `ROLE_MANAGER`.
4. Преобразует сотрудника в `EmployeeEntity`.
5. Кодирует пароль через настроенный `PasswordEncoder` (BCrypt) и сохраняет хэш.
6. Сохраняет учётную запись.
7. Возвращает `EmployeeDTO`.
8. Публикует интеграционное событие `USER_REGISTERED`.

Пароль в доменную модель `Employee` и обычный `EmployeeDTO` не передаётся.

### 6.3. Создание сотрудника администратором

Сценарий `AuthService.createEmployee()`:

1. Проверяет совпадение пароля и подтверждения.
2. Проверяет уникальность email.
3. Создаёт доменного сотрудника с ролью, указанной в `CreateEmployeeDTO`.
4. Создаёт `EmployeeEntity`, кодирует пароль и сохраняет запись.
5. Возвращает `EmployeeDTO`.
6. Публикует событие `EMPLOYEE_CREATED`.

Операция вызывается из административного UI и REST API. В REST-контроллере доступ ограничен ролью администратора на уровне класса.

### 6.4. Просмотр сотрудников и профилей

Реализованы следующие операции сервиса:

- получение сотрудника по email;
- получение сотрудника по ID;
- получение списка сотрудников;
- получение одного профиля по ID;
- получение списка профилей;
- получение текущего сотрудника из `SecurityContext`;
- проверка существования email.

Список сотрудников сортируется по ID. `EmployeeDTO` используется для административных операций, а `ProfileDTO` — для отображения профиля без пароля.

### 6.5. Изменение данных сотрудника и роли

Администратор может изменить имя, фамилию, email и роль существующего сотрудника. Перед обновлением REST-контроллер проверяет, что новый email не занят другим сотрудником. Сервис:

1. требует существующий ID;
2. загружает текущую `EmployeeEntity`;
3. создаёт доменный `Employee` из DTO;
4. переносит доменные данные в существующую сущность;
5. сохраняет сущность.

Пароль при таком обновлении не меняется: `EmployeeEntityMapper.updateEntity()` обновляет только имя, фамилию, email, дату регистрации и роль. ID и хэш пароля сохраняются в существующей сущности.

Отдельный доменный метод `changeRole()` существует, но текущий сценарий обновления сотрудника использует создание доменного объекта из DTO и маппинг его полей.

### 6.6. Смена пароля

Смена пароля выполняется через `AuthService.changePassword(employeeId, newPassword)`:

1. Загружается сотрудник по ID.
2. Новый пароль кодируется через `PasswordEncoder`.
3. Хэш сохраняется в `EmployeeEntity`.
4. Публикуется событие `PASSWORD_CHANGED`.

В UI предусмотрены сценарии смены собственного пароля и смены пароля сотрудника администратором. Пароль не проходит через `EmployeeDTO`.

Внутри `AuthService.changePassword()` проверяется существование сотрудника; совпадение нового пароля с подтверждением проверяется на уровне UI-контроллера. Отдельного сценария восстановления пароля по email/одноразовой ссылке в текущем коде не подтверждено.

### 6.7. Удаление сотрудника

Физическое удаление сотрудника через прикладной сценарий не выполняется. Административная операция `EmployeeService.deactivateById()` устанавливает `EmployeeEntity.active = false`, а `activateById()` повторно активирует учётную запись. Запись сотрудника сохраняется, поэтому внешние ключи проектов на создателя и последнего редактора не нарушаются.

Состояние активности относится к persistence/security-уровню и не включено в доменную модель `Employee`. Признак хранится в колонке `employee.is_active`. `EmployeePrincipal.isEnabled()` отражает это состояние. Вход, обновление Refresh JWT и обработка каждого Access JWT проверяют активность сотрудника; для деактивированной учётной записи фильтр очищает токены и не устанавливает аутентификацию. Администратор может активировать учётную запись повторно.

### 6.8. Валидация и ограничения учётной записи

В DTO применяются проверки обязательности имени, фамилии и email; email ограничен 50 символами и проверяется форматом, фамилия — 20 символами. Для пароля и подтверждения в DTO регистрации/создания задана максимальная длина 120 символов. Совпадение пароля с подтверждением проверяется сервисом.

Проверка уникальности email выполняется прикладным кодом; в JPA-сущности также задано ограничение уникальности. Точная политика нормализации регистра email и единый формат ошибок должны рассматриваться отдельно: в текущем описании нельзя предполагать, что email автоматически приводится к нижнему регистру.

### 6.9. Вход, обновление токенов и выход

**Вход пользователя:**

1. Пользователь передаёт email и пароль.
2. `EmployeeService.loadUserByUsername()` загружает `EmployeeEntity` и формирует `EmployeePrincipal`.
3. `AuthService.login()` сравнивает введённый пароль с сохранённым BCrypt-хэшем.
4. При успехе создаётся Authentication и помещается в `SecurityContext`.
5. Генерируются access- и refresh-токены.
6. Публикуется событие `USER_LOGGED_IN`.

Access token содержит ID, роль, тип токена и email в subject. Refresh token содержит subject, тип и UUID-значение `ver`. Для access и refresh используются разные секреты и сроки действия, задаваемые конфигурацией.

**Обновление токенов:**

- REST endpoint принимает refresh token в заголовке `Refresh-Token`.
- Для MVC-фильтра токены читаются из cookies `jwtAccess` и `jwtRefresh`.
- При истечении или отклонении access token фильтр пытается проверить refresh token, загружает актуальный principal и выпускает новую пару токенов.
- Для REST-ответа новые токены возвращаются в заголовках `Authorization` и `Refresh-Token`; для MVC — в HttpOnly cookies.
- В REST-сценарии отсутствующий refresh token приводит к ответу 400, недействительный/истёкший — к 401.

**Выход:**

REST endpoint `/api/v1/logout` удаляет cookies `jwtAccess` и `jwtRefresh`, устанавливая для них `Max-Age=0`. MVC logout настроен в Spring Security и также удаляет эти cookies. Серверного хранилища сессий или списка отозванных JWT в проверенной реализации нет. Событие `USER_LOGGED_OUT` при выходе не публикуется, несмотря на наличие такого значения в enum событий.

**Текущие особенности безопасности:**

- Spring Security настроен на `STATELESS`.
- CSRF отключён в `SecurityConfiguration`.
- Access и refresh JWT подписываются HS256 с разными секретами.
- Cookies устанавливаются с HttpOnly и Path=/; Secure и SameSite в коде генерации явно не задаются.
- `EmployeePrincipal` всегда сообщает, что учётная запись активна, не заблокирована и не просрочена.

Эти факты описывают текущую реализацию, но не являются утверждением о достаточности её безопасности.

## 7. Согласованное правило редактирования одного экземпляра ALS

<badge>Согласованное правило, реализация требует доработки</badge>

Редактирование одной выбранной ALS должно менять только один экземпляр в составе выбранного проекта. Другие экземпляры той же конфигурации и другие проекты, использующие общую сохранённую конфигурацию, должны оставаться без изменений.

Пример:

- в проекте три экземпляра одной конфигурации ALS, каждый на 20 ячеек;
- пользователь выбирает один экземпляр и меняет его конфигурацию на 24 ячейки;
- ожидаемый состав: две ALS по 20 ячеек и одна ALS по 24 ячейки;
- проекты, использующие исходную конфигурацию ALS, сохраняют прежнее состояние.

Это правило не означает обязательное дублирование всех `ModuleEntity`. Равные конфигурации модулей могут переиспользоваться, если они не разделяют изменяемое состояние, которое должно быть независимым.

### 7.1. Проверенное поведение текущей реализации

Текущий код реализует согласованное правило редактирования одного экземпляра:

1. `ProjectService.replaceALSandSaveProject()` находит выбранную ALS в DTO проекта по persistence ID.
2. Восстанавливает доменный Project и обе конфигурации ALS.
3. `Project.replaceALS(oldALS, newALS)` уменьшает количество исходной конфигурации на одну единицу и добавляет одну единицу новой.
4. `ALSService.saveALS()` выполняет Find-or-Create без обновления существующей `ALSEntity`.
5. `ProjectEntityMapper.updateEntity()` сохраняет ID существующей связи Project–ALS, если ALS остаётся в составе проекта; исчезнувшие связи удаляются, новые создаются.
6. Вся последовательность выполняется в транзакции `ProjectService`; вложенные сервисные вызовы используют распространение REQUIRED.

### 7.2. Оставшиеся ограничения

- `ALSDtoMapper` передаёт физический порядок через `moduleOrder`: каждый элемент ссылается на LB по индексу в `lbList` либо на единственный LC/LBC. Маппер проверяет полноту ссылок, отсутствие повторов и соответствие производного `positionControlModule` физическому порядку. Если `moduleOrder` отсутствует, для обратной совместимости применяется прежнее восстановление по позиции управляющего модуля с балансировкой сторон.
- Find-or-Create выполняет поиск кандидатов и полное сравнение под общей транзакционной блокировкой строки `find_or_create_lock` (`SELECT ... FOR UPDATE`). Блокировка используется в `ALSService`, `LBService`, `LCService` и `LBCService` и удерживается до commit/rollback. Репозитории выполняют поиск кандидатов с `PESSIMISTIC_WRITE`, то есть как locking reads: это важно при `REPEATABLE READ`, когда транзакция могла создать snapshot до ожидания mutex. В совокупности механизм сериализует операции создания конфигураций между экземплярами приложения и исключает гонку «проверка — вставка» при условии, что все пути записи проходят через эти сервисы.
- Удаление ALS из библиотеки выполняется отдельно от удаления связи из проекта. При наличии ссылок БД отклоняет физическое удаление через FK RESTRICT.

Массовое редактирование всех одинаковых экземпляров — отдельный сценарий и не является поведением по умолчанию.

## 8. Транзакционность и целостность

Сервисы проекта и ALS используют транзакции Spring. При обычном распространении транзакции REQUIRED вложенные вызовы сервисов участвуют в общей транзакции вызывающего метода.

Транзакция объединяет в одну атомарную операцию сохранение новых модулей, ALS и обновление состава проекта. При исключении изменения откатываются. Конфигурации Module/ALS не обновляются на месте: существующие записи переиспользуются только при полном совпадении, а изменённые сохраняются как новые. Find-or-Create дополнительно защищён общей блокировкой строки БД, удерживаемой до завершения транзакции; поэтому параллельные операции записи конфигураций сериализуются.

## 9. Известные ограничения и вопросы для последующей доработки

| Область | Текущее состояние / риск |
|---|---|
| Замена ALS в домене | Реализована заменой одной единицы конфигурации |
| Общая ALSEntity | Find-or-Create не обновляет существующую конфигурацию по входному ID |
| Выбор ALS в проекте | Выбранная конфигурация проверяется в составе загруженного проекта |
| Удаление ALS из проекта | Уменьшается количество на одну единицу; сохранённая ALS не удаляется |
| Ключи Project | Внутренние ключи ALS защищены копированием; наружу выдаются независимые копии |
| DTO и domain | DTO хранит физический список, domain агрегирует количество |
| Идентификаторы | Persistence ID не входят в доменную модель; соответствие обеспечивается на прикладной границе |
| Конкурентный Find-or-Create | Общая транзакционная блокировка строки БД; интеграционный тест проверяет сериализацию конкурирующих транзакций |
| Порядок модулей в DTO | Передаётся явным списком ссылок `moduleOrder`; старый формат без него поддерживается при чтении |

Перечисленные ограничения отражают текущее состояние; устранённые ранее расхождения не следует повторно считать открытыми задачами.

## 10. Интеграционные события и уведомления пользователей

В приложении существует прикладная интеграция между `lb-calc-web` и отдельным модулем `notification-service` через Kafka.

### 10.1. Формирование событий

`AuthService` формирует `UserEvent` с полями:

- `type` — тип события;
- `userId` — ID учётной записи;
- `email` — email получателя.

Событие отправляется через `KafkaTemplate` в topic, имя которого задаётся свойством `app.kafka.topic.user-events` (значение берётся из `KAFKA_TOPIC_USER_EVENTS`). В качестве Kafka key используется ID пользователя.

В текущем коде `AuthService` фактически публикует события:

| Событие | Точка публикации |
|---|---|
| `USER_REGISTERED` | Самостоятельная регистрация |
| `USER_LOGGED_IN` | Успешный вход |
| `EMPLOYEE_CREATED` | Создание сотрудника администратором |
| `PASSWORD_CHANGED` | Смена пароля |

В enum также объявлены `USER_LOGGED_OUT`, `PASSWORD_RESET_REQUESTED` и `EMPLOYEE_UPDATED`, но проверенные сценарии `AuthService` не публикуют эти события. Наличие значения enum и обработчика в consumer не означает, что соответствующий сценарий реализован end-to-end.

### 10.2. Обработка событий

`notification-service` содержит Kafka consumer, который получает `UserEvent` и передаёт его в `NotificationService.process()`. По типу события формируются тема и текст уведомления.

**Ограничение текущей реализации:** `EmailNotificationService.send()` не отправляет письмо через SMTP или внешний почтовый сервис. Сейчас он только выводит адрес, тему и текст в стандартный вывод процесса. Следовательно, реализована обработка события и формирование содержимого уведомления, но фактическая доставка email не реализована.

### 10.3. Несогласованность настройки Kafka topic

В producer имя topic читается из `KAFKA_TOPIC_USER_EVENTS`, а `@KafkaListener` в `UserEventConsumer` указывает строковый литерал `user-events-topic`. Если значение переменной окружения не совпадает с этим литералом, producer и consumer будут работать с разными topic. Это текущее техническое расхождение конфигурации, а не бизнес-правило.

### 10.4. Границы ответственности

Kafka-события формируются в прикладном `AuthService`, а не доменными агрегатами. Они не являются доменными событиями `Employee` и не должны описываться как часть поведения доменной модели.

## 11. Неполностью реализованные и не подтверждённые сценарии

Следующие функции встречаются в функциональных/проектных документах или следуют из названий типов событий, но не подтверждены как полностью реализованные в текущем коде:

## 13. Сводная фиксация согласованных бизнес-правил

Раздел объединяет решения, принятые при уточнении домена и бизнес-логики. Он отделяет согласованные правила от текущего поведения кода и от вопросов, по которым решение ещё не принято. Если более ранний раздел этого документа описывает фактическое поведение, а не целевое правило, следует учитывать явную пометку «текущая реализация» и этот раздел.

### 13.1. Проект, количество и редактирование одной ALS

1. Доменный Project агрегирует одинаковые конфигурации ALS в `Map<ALS, Integer>`. Порядок ALS в проекте не имеет значения.
2. DTO представляет физические экземпляры списком `alsList`; при преобразовании в домен количество вычисляется по списку. `quantityALS` не является независимым полем DTO.
3. Persistence хранит количество в связи Project–ALS. ID связи и ID конфигурации ALS имеют разный смысл.
4. Редактирование выбранной ALS меняет только одну единицу количества. Для трёх одинаковых ALS после изменения одной должны остаться две исходные и одна новая конфигурация.
5. Другие проекты, ссылающиеся на исходную ALS, не должны изменяться. Сохранённая конфигурация не обновляется на месте в сценарии редактирования одного экземпляра.
6. Прикладной сценарий получает выбранную ALS из состава проекта, создаёт глубокую независимую копию, применяет изменения и заменяет одну единицу в Project. Полностью равные конфигурации могут быть повторно использованы.
7. Массовое изменение всех одинаковых ALS — отдельный сценарий.
8. Эти правила согласованы и реализованы в текущем сценарии `ProjectService.replaceALSandSaveProject()`: `Project.replaceALS()` заменяет одну единицу количества.

### 13.2. Структура ALS и модулей

- `LB` выполняет хранение; `LC` — управление; `LBC` — один физический комбинированный модуль, одновременно выполняющий обе роли.
- ALS содержит ровно один управляющий модуль (LC/LBC) и не менее одного storage-модуля (LB/LBC).
- Допустимы один LC и один или более LB либо один LBC и ноль или более LB. Для CENTER количество LB слева и справа должно различаться не более чем на один; для одиночного LBC применяется нейтральное техническое значение CENTER. Фактическое число модулей дополнительно ограничивается геометрическими и размерными валидаторами.
- Порядок модулей в ALS значим и соответствует расположению слева направо; это единственный источник истины о физическом составе. DTO сохраняет его через `moduleOrder`, persistence — через `ALSModuleEntity.moduleOrder`. Нумерация ячеек идёт последовательно слева направо по модулям и ячейкам.
- Положение управляющего LC/LBC вычисляется по его позиции в списке. LEFT означает управляющий модуль слева и LB справа; RIGHT — LB слева и управляющий модуль справа; CENTER — LB по обе стороны управляющего модуля.
- Правила позиционирования одинаковы для LC и LBC. При добавлении LB в LEFT он размещается справа от управляющего модуля; при RIGHT — слева. При CENTER новые LB распределяются по обе стороны так, чтобы разница между количеством LB слева и справа не превышала одного; новый LB добавляется на менее заполненную сторону, а при равенстве допустима любая сторона.
- Для одиночного LBC техническое значение CENTER принято как нейтральное значение по умолчанию; оно не обозначает физическое центральное положение и не должно показываться пользователю как реальная позиция.

### 13.3. Оборудование и функции

- `EquipmentConfiguration` входит в LC/LBC. Оборудование не является отдельным элементом списка модулей ALS.
- Функциональные возможности выводятся из конфигурации управления и характеристик оборудования; отдельная сохраняемая «конфигурация функциональности» не вводится.
- `FunctionalSelection` — временное состояние выбора пользователя в конфигураторе, не сохраняемая часть конфигурации.
- `FunctionalSelection` является временным выбором оплаты, дисплея (нет/10″/17″/19″) и способов доступа. Подбор оборудования выполняется по этим трём группам. Целевое двустороннее преобразование восстанавливает функциональные признаки из фактической `EquipmentConfiguration`; отдельный сохраняемый `FunctionalSelection` не вводится. `PrintOption` не используется как независимый сохраняемый выбор; необходимость принтера определяется оплатой и способами доступа. Конкретные модели и количество оборудования хранятся в `EquipmentConfiguration`.
- Пользователь выбирает функции; единый целевой `EquipmentRequirementResolver` для LC/LBC определяет требования и подставляет совместимую комплектацию по умолчанию.
- Пользователь может заменить предложенную модель другой совместимой. При изменении функций сохраняется оборудование, нужное другим функциям; неиспользуемое автоматически подобранное оборудование удаляется, если оно не закреплено вручную.
- Один компонент может обеспечивать несколько функций и в физической комплектации присутствует один раз. Доступные аппаратные возможности определяются выбранными моделями оборудования.
- Для каждой доступной пользователю функции каталог обязан обеспечивать совместимую модель по умолчанию. Отсутствие такой модели — нарушение целостности каталога, а не штатная пользовательская ошибка. Несовместимую или неполную комплектацию сохранить нельзя.
- Дисплей в LC/LBC ровно один; допустимые диагонали — 10, 17 и 19 дюймов. Разные позиции каталога с разными ID являются разными моделями.
- Идентичность позиции оборудования в составе — каталожный ID; количество хранится отдельно, порядок элементов не влияет на идентичность.
- Домен не обращается к сервисам и репозиториям. ProjectService координирует проектный сценарий и изоляцию выбранной ALS; ALS отвечает за состав и порядок модулей; каждый тип модуля — за собственные параметры и пересчёт.

### 13.4. Идентичность и жизненный цикл

- Целевое правило — сохранённые конфигурации неизменяемы; изменение выполняется через Find-or-Create: найти полностью равную конфигурацию или создать новую.
- Идентичность ALS учитывает характеристики и упорядоченный состав модулей.
- Для позиции оборудования в сохранённой комплектации идентичность определяется конкретной каталожной позицией по ID; количество хранится отдельно. Разные ID означают разные позиции, даже если часть характеристик совпадает.
- Порядок записей оборудования не влияет на идентичность комплектации. Дисплей имеет quantity=1.
- Прежнее противоречие между бизнес-полями Equipment и парой `equipmentId + quantity` закрыто в пользу каталожного ID и отдельного количества для состава конфигурации.
- Жизненный цикл по ТЗ: DRAFT → SAVED/IMMUTABLE → USED → ORPHAN; архивация администратором. Архивирование не равно физическому удалению.
- Неизменяемость сохранённых конфигураций Module/ALS и Find-or-Create для них реализованы. Отдельный persistence-каталог Equipment и полный жизненный цикл DRAFT/SAVED/USED/ORPHAN с архивированием не реализованы.

### 13.5. Геометрические формулы

Все линейные величины ниже — миллиметры.

```text
Ширина ячейки = ширина модуля - deltaWidth - serviceZoneWidth
Глубина ячейки = глубина модуля - doorThickness
Полезная высота = высота модуля - upperFrame - bottomFrame
                  - (countCells - 1) * shelfThick
Высота ячейки = полезная высота / countCells
Ширина ALS = сумма ширин всех модулей ALS
```

- Дробная часть высоты ячейки отбрасывается (приведение к целому вниз), математическое округление не применяется.
- Общие параметры ALS — высота, глубина, верхняя/нижняя рамы и цвета корпуса/дверей — синхронизируются с модулями.
- Направление дверей обычного LB зависит от стороны относительно управляющего модуля: слева от него — LEFT, справа — RIGHT. Для самого LBC действует отдельное правило: LEFT — RIGHT; CENTER — LEFT; RIGHT — LEFT. Для одиночного LBC используется техническое нейтральное CENTER, поэтому направление дверей — LEFT.
- Текущий код `StorageModule` рассчитывает ширину ячейки как `moduleWidth - deltaWidth - serviceZoneWidth`.
- Проверка минимальной ширины модуля и ширины ячейки в `ModuleSizeValidator` также учитывает `serviceZoneWidth`.

### 13.7. Динамические ограничения и проверки

Текущий `SizeValidator` выполняет валидацию DTO на уровнях LB, LC, LBC, ALS и Project. Глубокая проверка ALS включает саму ALS, её LC или LBC и все LB; проверка проекта обходит каждую ALS.

- **LB:** верхняя/нижняя рамы 20–300; тип и его параметры должны быть заданы и находиться в границах; минимальная высота модуля = max(125, 85 + верхняя рама + нижняя рама); глубина 170–900; минимальная ширина модуля = 100 + deltaWidth, максимум 1200; толщина дверцы 5–50.
- **LB, количество ячеек:** динамический максимум = min(20, floor((полезная высота + shelfThick) / (85 + shelfThick))). Дополнительно проверяется фактическая высота ячейки не менее 85 мм.
- **LB, ячейка:** глубина = глубина модуля − толщина дверцы и должна быть 100–880; ширина = ширина модуля − deltaWidth и в текущем валидаторе должна быть не меньше 100 и не больше 1200 − deltaWidth.
- **LC:** рамы 20–300; высота 600–2300; глубина 170–900; полезная высота после вычета рам должна быть не менее 300 для панели управления.
- **ALS:** рамы 20–300; высота 125–2300; глубина 170–900; требуется управляющий модуль и хотя бы один модуль хранения; полезная высота после вычета рам должна быть не менее 85 для ячейки и не менее 300 для панели управления.
- **LBC:** рамы 20–300; параметры типа проверяются в тех же пределах, что и для LB; высота не ниже max(125, 85 + верхняя рама + нижняя рама) и не выше 2300; глубина 170–900; минимальная ширина — максимум из (100 + deltaWidth + serviceZoneWidth) и требуемой ширины установленного оборудования; максимальная ширина 1200; толщина дверцы 5–50; количество ячеек ограничено динамической формулой как у LB; проверяются размеры ячейки и полезная высота панели не менее 300.
- **Ширина оборудования LBC:** текущий валидатор определяет требуемую ширину по дисплеям LC10/LC17/LC19; для NONE/пустого/неизвестного имени возвращает 0. Это конкретное поведение текущего валидатора, не отдельное согласованное бизнес-правило каталога оборудования.
- **Параметры типа:** deltaWidth 0–500; shelfThick 0–100; serviceZoneWidth 0–300. Проверка параметров типа выполняется и при валидации LB/LBC.
- Валидация геометрии не заменяет структурную проверку доменной ALS. В домене ALS отдельно проверяется наличие ровно одного ControlModule и хотя бы одного StorageModule.

### 13.8. Формирование названий и описаний: текущие шаблоны кода

Названия и описания модулей и ALS — производные представления конфигурации. Они пересчитываются при соответствующем `recalculate()`; не должны становиться самостоятельными параметрами идентичности.

| Объект | Название в текущем коде | Состав описания в текущем коде |
|---|---|---|
| LB | `Модуль хранения на {countCells} ячеек` | Количество ячеек, тип LB, рассчитанные размеры ячейки (В×Ш×Г), габариты модуля (В×Ш×Г), направление открытия дверей, цвета корпуса/дверей, толщина дверцы |
| LC | `Модуль управления {displayName}`; при отсутствии дисплея — «Без дисплея» | Дисплей, габариты LC, верхняя/нижняя рамы, способы доступа, варианты печати, оплата, имена оборудования, цвета корпуса/дверей |
| LBC | `Комбинированный модуль на {countCells} ячеек` | Параметры хранения (количество ячеек, тип, размеры ячейки, габариты, направление дверей, цвета, толщина дверцы) и параметры управления (дисплей, способы доступа, варианты печати, оплата, установленное оборудование) |
| ALS | `АКХ на {totalCells} ячеек` | Общее количество ячеек, габариты ALS, цвета, количество и состав модулей в физическом порядке, описание управляющего модуля |

Особенности:
- В описании LC способы доступа и печати перечисляются по enum name в квадратных скобках; оборудование перечисляется по `Equipment.getName()`.
- Название LC зависит только от имени найденного дисплея (либо «Без дисплея»), а не от всех функций управления.
- Описание LBC должно включать не только параметры хранения, но и способы доступа, печати, оплату и фактически установленное оборудование.
- Описание ALS должно отражать весь состав модулей в физическом порядке, а не только количество storage-модулей и управляющий модуль.
- Целевой порядок пересчёта ALS: проверка структуры → синхронизация общих параметров → определение положения управляющего модуля → расчёт направлений дверей → пересчёт модулей и ячеек → нумерация ячеек → сумма ширин → формирование названий и описаний.
- Состав целевых шаблонов названий и описаний согласован; прежняя формулировка об открытом вопросе по LBC/ALS больше не актуальна.

### 13.9. Сотрудники и разграничение доступа

- Employee — доменная модель сотрудника; пароль/хэш и JWT остаются вне домена. Отдельная доменная сущность UserAccount не вводится; EmployeeEntity может хранить учётные данные на persistence/security-уровне.
- Менеджер видит все проекты, но изменяет только собственные; администратор может изменять любые.
- Сотрудник с существующими проектами не удаляется физически: выполняется деактивация, блокирующая авторизацию и сохраняющая ссылки на автора/редактора. Статус активности относится к EmployeeEntity/security-слою.

### 13.10. Гостевые проекты

- Гостевые проекты хранятся в IndexedDB и не сохраняются на сервере до импорта.
- После входа/регистрации можно выбрать проекты для импорта; сервер повторно валидирует их и определяет владельца по аутентифицированному пользователю.
- Локальная копия удаляется только после подтверждённого успешного сохранения; при ошибке остаётся доступной для повтора.
- Расчёты и проверки должны использовать общие доменные правила.
- Для каждого локального проекта используется постоянный guestProjectId как ключ идемпотентности. Повтор того же ID возвращает результат первоначального импорта и не создаёт дубликат.
- Разные guestProjectId не дедуплицируются только по названию. При похожем проекте допускается предупреждение, но автоматическая перезапись существующего проекта запрещена.
- При ошибке или неопределённом результате локальная копия сохраняется; удаление возможно только после подтверждения успешного сохранения на сервере.
- Сквозная реализация сценария пока не подтверждена.

### 13.11. Вопросы, отложенные за рамки текущего этапа

Незакрытых вопросов домена и бизнес-логики, необходимых для текущего этапа проектирования, нет.

Функциональный резолвер не назначает базовое оборудование. Физические электронные замки (`ELECTRONIC_LOCK`), их количество и распределение по ячейкам остаются отдельной будущей доработкой.

Правила распределения LB при CENTER, матрица функциональности и оборудования, происхождение автоматически подобранных позиций, уникальность default-модели и деактивация оборудования согласованы и не являются открытыми вопросами.

### 13.12. Согласованные правила выбора функциональности и подбора оборудования

Этот раздел фиксирует целевое поведение конфигуратора. Он не утверждает, что соответствующий сценарий уже полностью реализован в коде.

**Выбор и отображение**

- Пользователь выбирает способы доступа и вариант оплаты.
- `FunctionalSelection` является временным состоянием конфигуратора, а не самостоятельной сохраняемой доменной сущностью.
- При каждом выборе или изменении функциональности система сразу пересчитывает состав оборудования и показывает пользователю конкретные подобранные модели. Результат не скрывается до сохранения.
- Пользователь может заменить предложенную модель на другую активную и совместимую модель.
- Отдельного признака «автоматически подобрано / вручную закреплено» нет. При изменении функциональности система удаляет оборудование, которое больше не требуется, и сохраняет оборудование, необходимое оставшимся функциям.
- Один компонент, необходимый нескольким функциям, включается в комплектацию один раз.
- Принтер не выбирается независимо: необходимость его установки определяется выбранными способами доступа и/или оплатой. Самостоятельный `PrintOption` как сохраняемый выбор не используется.

**Матрица функциональности**

| Функциональность | Требование к оборудованию / ограничение |
|---|---|
| RFID | RFID-считыватель |
| BARCODE | Считыватель штрихкодов |
| QR | QR-считыватель |
| PIN | Дисплей 10″, 17″ или 19″ и минимум один дополнительный способ доступа: RFID, BARCODE или QR |
| Наличная оплата | Оборудование приёма наличных |
| Безналичная оплата | Банковский терминал |
| Наличная и безналичная оплата | Оборудование приёма наличных и банковский терминал |
| Любая ненулевая оплата | Принтер обязателен |
| BARCODE, QR или PIN | Принтер обязателен |
| Только RFID без оплаты | Принтер автоматически не требуется |

PIN не может быть единственным способом доступа. Если выбран PIN, должен быть выбран хотя бы один из способов RFID, BARCODE или QR, а дисплей обязателен.

**Каталог оборудования**

- Для каждого требования/категории допускается ровно одна активная модель по умолчанию.
- Для каждой доступной функции должна существовать совместимая модель по умолчанию. Отсутствие такой модели — нарушение целостности каталога, а не штатная ошибка пользователя.
- Деактивированная модель остаётся в ранее сохранённых конфигурациях.
- При редактировании конфигурации с уже установленной неактивной моделью её разрешено оставить без изменений. Повторно выбрать или добавить эту модель нельзя.
- Неактивные модели недоступны для выбора в новых конфигурациях.
- Физическое удаление модели, используемой сохранёнными конфигурациями, не допускается; вместо него применяется деактивация.
