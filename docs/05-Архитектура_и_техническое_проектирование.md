# 2. АРХИТЕКТУРА СИСТЕМЫ

## 2.1. Общая схема

Система построена по микросервисной архитектуре:

- **lb-calc-web** — основное веб-приложение (Spring Boot + Thymeleaf). Отвечает за UI, бизнес-логику, расчёты, работу с БД и аутентификацию.
- **notification-service** — отдельный сервис обработки Kafka-событий пользовательских учётных записей. В текущей реализации он формирует содержимое уведомлений; фактическая отправка email не реализована, содержимое выводится в консоль.
- **Инфраструктура** — MySQL 8.4 (хранение), Kafka (асинхронная коммуникация), Docker/Docker Compose (развёртывание).

## 2.2. Стек технологий

- **Backend:** Java 17, Spring Boot 3.5.3, Spring Data JPA, Spring Security, Spring Kafka.
- **Frontend:** Thymeleaf (Server-Side Rendering), HTML5, CSS3.
- **Безопасность:** JWT (Access + Refresh tokens в HTTP-only cookies), BCrypt.
- **Инструменты:** Maven, Spring Boot Test, Apache POI (экспорт в Excel), Flyway. Liquibase в проекте не используется.

## 2.3. Принципы архитектуры

- **Чистая архитектура:** Зависимости направлены внутрь, к Domain-слою. Domain не знает о Spring, JPA или HTTP.
- **Повторное использование конфигураций:** сервисы LB/LC/LBC и ALS применяют Find-or-Create. Сохранённые конфигурации модулей и ALS не обновляются по входному ID; изменённая конфигурация создаётся как новая запись. Проект и сотрудник обновляются своими сценариями.
- **Разделение ответственности:** Controller (HTTP) → Application Service (оркестрация) → Domain Model (инварианты и расчёты) / Repository (персистентность). Отдельный слой Domain Services с resolver-компонентами в текущей реализации не подтверждён.

# 3. СТРУКТУРА ПРИЛОЖЕНИЯ

## 3.1. Пакетная структура (com.lb_calc_web)

- **controller** — UI HTTP-контроллеры (приём/отдача запросов, маппинг на Thymeleaf view).
- **controller.api** — REST API контроллеры (для внешних интеграций, возвращают JSON).
- **service** — Application Services (оркестрация транзакций).
- **service.util** — Прикладные компоненты расчётов и проверок: SizeValidator (фасад), ModuleSizeValidator, ALSSizeValidator, ProjectSizeValidator, SizeBounds, а также сервисы изображений.
- **domain.model** — Доменные модели конструкции и проекта (ALS, LB, LC, LBC, Project).
- **domain.equipment** — Доменные типы оборудования.
- **domain.attributes** — Value Objects и Enums (Colors, TypeLb, AccessMethod).
- **domain.service** — отдельный пакет доменных сервисов в текущей структуре не подтверждён; расчёты и инварианты находятся в доменных моделях, прикладная оркестрация — в сервисном слое.
- **entity** — JPA-сущности (отображение на БД).
- **repository** — Интерфейсы Spring Data JPA.
- **dto** — Data Transfer Objects для передачи данных между слоями.
- **mapper** — Преобразования DTO ↔ Domain ↔ Entity (без бизнес-логики).
- **security** — Конфигурация Spring Security, JWT-сервисы, EmployeePrincipal.
- **События пользователя** — прикладной `UserEvent`, формируемый `AuthService` для Kafka. Это не доменные события агрегатов.

## 3.2. Правила зависимостей

- Controller вызывает только Service.
- Service вызывает Domain и Repository.
- Domain не зависит ни от чего внешнего (чистая Java).
- Mapper не содержит бизнес-логики и не обращается к БД.
- Repository не содержит бизнес-логики, только persistence-операции.

# 4. ДОМЕННАЯ МОДЕЛЬ (Краткая сводка)

В текущей доменной модели представлены следующие основные объекты:

- **Project** — доменная модель проекта, хранит конфигурации ALS и их количество в `Map<ALS, Integer>`.
- **ALS** — агрегат конструкции, содержит упорядоченный список модулей, проверяет структурные инварианты и выполняет пересчёт конструкции.
- **Module / StorageModule / ControlModule** — иерархия модулей; конкретные типы LB, LC и LBC. Модули входят в состав ALS.
- **Employee** — доменная модель сотрудника с именем, фамилией, email, датой регистрации и ролью.
- **Equipment** — доменная абстракция оборудования; позиции из БД представлены через `CatalogEquipment`. Каталог хранится в `equipment_catalog` и управляется через `EquipmentCatalogService`; отдельного агрегата Equipment нет.

Текущие доменные объекты изменяемы. Их нельзя описывать как полностью неизменяемые после сохранения.

# 5. КЛЮЧЕВЫЕ АЛГОРИТМЫ

## 5.1. EquipmentRequirementResolver (реализован)

Класс `service.EquipmentRequirementResolver` преобразует функциональные настройки LC/LBC в требования к моделям оборудования. Он вызывается `LCService` и `LBCService` при создании/сохранении модулей, а также `ALSService` при восстановлении управляющего модуля из DTO. `ProjectService` использует тот же сценарий через `ALSService.restoreDomain`.

Резолвер формирует требования только из выбранных функциональных параметров. Категории базового и дополнительного оборудования вне функциональной матрицы не изменяются:

- LOCK_CONTROLLER, COMPUTER, POWER_SUPPLY и UPS не добавляются и не удаляются функциональным резолвером; уже выбранные позиции сохраняются.
- CASH → CASH_ACCEPTOR.
- CASHLESS → PAYMENT_TERMINAL.
- CASH_AND_CARDS → PAYMENT_TERMINAL + CASH_ACCEPTOR.
- RFID → RFID_READER.
- BARCODE → BAR_READER с поддержкой 1D или 2D.
- QR_CODE → BAR_READER с поддержкой 2D.
- Выбранный DISPLAY (10/17/19 дюймов) сохраняется независимо от PIN; PIN без выбранного дисплея требует активную модель DISPLAY по умолчанию и как минимум один дополнительный способ доступа RFID/BARCODE/QR_CODE.
- Ненулевой способ оплаты, BARCODE, QR_CODE или PIN → PRINTER. Только RFID без оплаты не требует принтера.
- Дополнительные категории (MODEM, ROUTER, ANTENNA) сохраняются в комплектации, но не добавляются автоматически без функционального требования.
- Физические ELECTRONIC_LOCK и их распределение по ячейкам остаются за рамками текущей реализации.

## 5.2. Подбор и размещение оборудования (реализованная часть и ограничения)

Каталог является единым справочником `equipment_catalog` с категориями DISPLAY, BAR_READER, PRINTER, RFID_READER, LOCK_CONTROLLER, PAYMENT_TERMINAL, CASH_ACCEPTOR, а также базового и дополнительного оборудования. Функциональный резолвер управляет только DISPLAY, BAR_READER, PRINTER, RFID_READER, PAYMENT_TERMINAL и CASH_ACCEPTOR; прочие категории сохраняются без пересчёта. Общие дополнительные категории MODEM, ROUTER и ANTENNA могут использоваться без специализированных доменных классов. Общая доменная модель `Equipment` предоставляет категорию и признаки поддерживаемых возможностей; `CatalogEquipment` переносит характеристики записи каталога.

1. Для требуемой категории выбирается ровно одна активная модель с признаком `is_default`. Отсутствие или неоднозначность модели по умолчанию считается ошибкой целостности; выбор первого подходящего элемента запрещён.
2. При создании/изменении модели по умолчанию `EquipmentCatalogService` снимает этот признак с прежней активной модели категории. Уникальный индекс БД дополнительно запрещает две активные модели по умолчанию одной категории.
3. Пользователь может передать список `equipmentSelections` с каталожными ID и количеством. Выбранная позиция разрешается только если она активна и совместима с требуемой функцией. Пользовательские формы пока не подключены к полному динамическому каталогу; этот этап отложен. При редактировании без `equipmentSelections` сервис сохраняет позиции из текущей записи БД, заменяя только выбранный дисплей; это предотвращает потерю пользовательских моделей и дополнительного оборудования.
4. Деактивированная модель недоступна для нового выбора. При редактировании сохранённой конфигурации она разрешена только если уже присутствовала в исходной комплектации; восстановление из БД выполняется через `resolveById`.
5. Для модели, используемой в LC/LBC, запрещено менять категорию, название, габариты и признаки совместимости. Физическое удаление блокируется внешним ключом; деактивация сохраняет исторические ссылки.
6. Состав сохраняется в `lc_equipment`/`lbc_equipment` как ID и количество. Группы required/additional в persistence не разделяются.
7. При изменении функций resolver удаляет позиции категорий, которые больше не требуются, сохраняет позиции оставшихся обязательных категорий и добавляет недостающие модели по умолчанию. Отдельного признака ручного закрепления оборудования нет.
8. CASH разрешается через CASH_ACCEPTOR; CASHLESS — через PAYMENT_TERMINAL; CASH_AND_CARDS — через обе категории. LOCK_CONTROLLER, COMPUTER, POWER_SUPPLY и UPS не управляются функциональным резолвером.

Для чтения LC/LBC каталог преобразуется в доменные позиции одним запросом и используется как единый resolver, включая деактивированные исторические модели. Ленивые коллекции состава оборудования, способов доступа и печати загружаются пакетами Hibernate (`@BatchSize(size = 50)`), чтобы не выполнять отдельный запрос для каждой сущности при чтении списков.

## 5.3. Find-or-Create для Module и ALS (реализовано)

Find-or-Create применяется к конфигурациям LB, LC, LBC и ALS. Для Equipment существует справочная таблица `equipment_catalog`, но отдельного JPA-агрегата Equipment нет: LC/LBC хранят ссылки на позиции каталога и количество внутри конфигурации.

1. Преобразовать входной DTO в доменную модель. Геометрическую валидацию выполнять только над Domain: ModuleSizeValidator проверяет LB/LC/LBC, ALSSizeValidator — общие параметры ALS и её модули, ProjectSizeValidator — уникальные конфигурации ALS в Project.
2. Выполнить SELECT кандидатов по базовым скалярным параметрам.
3. Восстановить доменные конфигурации кандидатов через Entity Mapper; при восстановлении проверить сохранённые производные поля.
4. Сравнить полные доменные конфигурации, включая физический состав оборудования и количество позиций.
5. При полном совпадении вернуть существующую сущность и её ID.
6. При отсутствии совпадения создать новую Entity; существующие конфигурации не обновлять.

Состав оборудования LC/LBC хранится в `lc_equipment`/`lbc_equipment` как `catalog_position_id + quantity`. Способы доступа и варианты печати хранятся в отдельных ElementCollection-таблицах.

**Конкурентный доступ:** перед поиском кандидатов сервис получает общую блокировку строки `find_or_create_lock` через `SELECT id FROM find_or_create_lock WHERE id = 1 FOR UPDATE`. Блокировка удерживается до commit/rollback внешней транзакции. Её используют `ALSService.saveALS()`, `LBService.saveLB()`, `LCService.saveLC()` и `LBCService.saveLBC()`. В сценарии ALS блокировка охватывает также разрешение и сохранение входящих модулей. Все запросы `findCandidates()` в репозиториях используют `PESSIMISTIC_WRITE`, поэтому выполняются как locking reads и читают актуальные зафиксированные данные даже при наличии более раннего snapshot в транзакции с `REPEATABLE READ`. Таким образом, операции Find-or-Create сериализуются между всеми экземплярами приложения.

## 5.4. Расчёт размеров ячеек (StorageModule.recalculateStorageCells)

- cellWidth = moduleWidth - typeLb.deltaWidth - typeLb.serviceZoneWidth
- cellDepth = moduleDepth - doorThickness
- usableHeight = moduleHeight - upperFrame - bottomFrame - ((countCells - 1) * typeLb.shelfThick)
- cellHeight = (int) (usableHeight / countCells); при countCells = 0 расчётное значение cellHeight равно 0, после чего валидатор сообщает о недопустимом количестве ячеек.
- **Инварианты:** cellWidth > 0, cellDepth > 0, cellHeight >= 85; допустимое количество ячеек проверяется с учётом полезной высоты и ограничения каталога.

## 5.5. Архитектура геометрической валидации (реализовано)

Проверка разделена по уровню ответственности и работает с доменными моделями:

- **ModuleSizeValidator** — диапазоны и геометрия доменных LB, LC и LBC: размеры модулей, рамы при самостоятельной проверке, ширина под оборудование, толщина дверцы, параметры типа хранения, количество и размеры ячеек.
- **ALSSizeValidator** — общие размеры ALS, достаточная полезная высота и защитная проверка структуры агрегата. Структурные инварианты (ровно один ControlModule и хотя бы один StorageModule) также обеспечиваются самой доменной ALS. При глубокой проверке валидатор передаёт модулям общие размеры из ALS, не дублируя проверку общих параметров.
- **ProjectSizeValidator** — проверяет каждую уникальную конфигурацию ALS из доменной Map<ALS, Integer>; количество экземпляров не меняет геометрическую корректность конфигурации.
- **SizeValidator** — фасад с методами, принимающими только доменные LB, LC, LBC, ALS и Project. DTO в сигнатурах валидаторов и фасада отсутствуют.
- **SizeBounds** — неизменяемый набор числовых ограничений, загружаемый из size-bounds.properties.

Расчёт производных размеров отделён от проверки ограничений. StorageModule.recalculateStorageCells вычисляет размеры ячеек и не прерывает создание доменной модели только из-за отрицательной/недостаточной геометрии. Проверку допустимости выполняет ModuleSizeValidator. Аналогично LC и LBC пересчитывают описание без самостоятельного исключения по недостаточной ширине оборудования; ширина проверяется валидатором. ALS по-прежнему немедленно отклоняет структурно недопустимую композицию.

Общие размеры ALS проверяются на уровне ALS один раз. При глубокой проверке модулей проверяются их собственные параметры (ширина, тип, толщина дверцы, число ячеек и геометрия ячеек). LBC остаётся одним физическим модулем и проверяется один раз, несмотря на совмещение ролей хранения и управления.

Валидаторы возвращают ValidationResult. Прикладные сервисы преобразуют результаты в ValidationSizeException. Идентификаторы persistence не являются частью доменных моделей, поэтому валидаторы не извлекают их из DTO. Для сохранения связи ошибок с элементами API прикладной сервис сопоставляет результаты с исходным DTO и добавляет идентификаторы только в транспортный результат. Ошибки преобразования входного DTO в доменную модель также переводятся прикладным сервисом в ValidationSizeException с типом и ID исходного объекта; они не должны обходить штатный механизм отображения ошибок формы. ValidationResult при добавлении ошибки переносит objectType и objectId в каждый ValidationError, а при последующем назначении objectId обновляет уже созданные ошибки.

# 6. API-КОНТРАКТЫ И ЭНДПОИНТЫ

Приведённые ниже таблицы описывают целевые API-контракты и варианты организации эндпоинтов. Они не являются подтверждением наличия всех перечисленных маршрутов в текущем коде. ### 6.3.3. Правила для REST API

1. **Версионирование:** Все эндпоинты имеют префикс `/api/v1/`. При изменении контракта создаётся `/api/v2/`.
2. **Аутентификация:** Используется JWT в заголовке `Authorization: Bearer {accessToken}`.
3. **Формат данных:** JSON (Content-Type: application/json).
4. **HTTP-методы:**
    - GET — чтение
    - POST — создание
    - PUT — полное обновление
    - PATCH — частичное обновление (не используется в текущей версии)
    - DELETE — удаление
5. **Коды ответов:**
    - 200 OK — успешное чтение/обновление
    - 201 Created — успешное создание
    - 204 No Content — успешное удаление
    - 400 Bad Request — ошибка валидации
    - 401 Unauthorized — не аутентифицирован
    - 403 Forbidden — нет прав
    - 404 Not Found — ресурс не найден
    - 409 Conflict — нарушение уникальности (например, email уже существует)
    - 500 Internal Server Error — внутренняя ошибка
6. **Обработка ошибок:** Все ошибки возвращаются в формате:

        {
          "timestamp": "2026-10-16T10:30:00",
          "status": 400,
          "error": "Validation Error",
          "message": "Email уже используется",
          "path": "/api/v1/employees"
        }

# 7. ПОСЛЕДОВАТЕЛЬНОСТИ ДЕЙСТВИЙ (Сценарии)

## 7.1. Создание проекта

1. Пользователь открывает `GET /projects/create`.
2. `ProjectController` вызывает `ProjectService.createProject()`.
3. Сервис создаёт начальный доменный `Project`, создаёт начальную ALS через `ALSService.createALS()` и преобразует модели в DTO для формы.
4. Пользователь редактирует состав проекта. Для ещё не сохранённого проекта добавление ALS изменяет DTO формы; сохранения в БД на этом этапе нет.
5. При отправке `POST /projects/{id}/save` контроллер передаёт `ProjectDTO` в `ProjectService.saveProject()`.
6. Сервис проверяет права, устанавливает серверные метаданные, восстанавливает Domain, валидирует проект и передаёт его в общий `persistProject()`.
7. `persistProject()` сохраняет уникальные конфигурации ALS через `ALSService.saveALS(ALS)`, разрешает их в `ALSEntity` и сохраняет `ProjectEntity`.

## 7.2. Добавление и удаление ALS в сохранённом проекте

Добавление:

1. Контроллер вызывает `ProjectService.addNewALSandSaveProject(projectId)`.
2. Сервис загружает `Project` из `ProjectEntity` через `ProjectEntityMapper`.
3. `ALSService.createALS()` создаёт новую доменную конфигурацию; `Project.addALS()` добавляет её в агрегат.
4. `saveDomainProject()` проверяет право изменения, обновляет автора изменения и валидирует агрегат.
5. Общий `persistProject()` сохраняет ALS и проект в одной транзакции.

Удаление:

1. Контроллер передаёт `projectId` и `alsId` в `ProjectService.deleteALSandSaveProject()`.
2. Сервис загружает доменный проект и находит ALS по ID внутри состава проекта.
3. `Project.removeALS()` уменьшает количество выбранной конфигурации на одну единицу.
4. Проект сохраняется через `saveDomainProject()` и `persistProject()`. Сама `ALSEntity` не удаляется, поскольку может использоваться другими проектами.

## 7.3. Замена конфигурации ALS в проекте

1. Пользователь открывает форму ALS по `projectId` и `alsId`; контроллер получает DTO выбранной конфигурации для представления.
2. После отправки формы контроллер передаёт в `ProjectService.replaceALSandSaveProject(projectId, alsId, alsDTO)` только идентификаторы маршрута и изменённый DTO. Повторно загружать и передавать целый `ProjectDTO` не требуется.
3. Сервис загружает доменный проект из БД и проверяет, что ALS с указанным ID действительно входит в его состав.
4. ID ALS назначается из маршрута. `ALSService.restoreDomain()` восстанавливает новую конфигурацию Domain.
5. `Project.replaceALS(oldALS, newALS)` заменяет ровно одну единицу исходной конфигурации. Остальные одинаковые ALS в проекте остаются без изменений.
6. `saveDomainProject()` проверяет права и валидирует агрегат; `persistProject()` выполняет Find-or-Create для ALS и сохраняет обновлённый проект.
7. В ответ контроллер получает DTO сохранённой конфигурации. При изменении содержимого ALS может получить новый persistence ID, поэтому результат сопоставляется по доменному содержимому, а не по прежнему ID.

## 7.4. Изменение модулей внутри ALS проекта

1. Контроллер получает DTO выбранной ALS и конкретного модуля по идентификаторам проекта, ALS и модуля.
2. При сохранении контроллер передаёт в `ProjectService` идентификаторы маршрута и DTO изменяемого модуля.
3. Сервис загружает доменный проект, находит ALS по ID и проверяет принадлежность конкретного LB/LC/LBC этой ALS.
4. Входной модуль восстанавливается в контексте исходной ALS. Для LC/LBC используется resolver сохранённой комплектации, чтобы не потерять дополнительное оборудование и разрешить ранее выбранные деактивированные позиции.
5. Сервис создаёт независимую копию ALS, применяет к ней доменную операцию добавления, удаления или замены модуля и передаёт результат в `Project.replaceALS()`.
6. `saveDomainProject()` проверяет право изменения и доменные ограничения; общий `persistProject()` сохраняет новые/переиспользуемые конфигурации ALS и обновляет проект в одной транзакции.

## 7.5. Find-or-Create модуля

1. Сервис получает доменную конфигурацию модуля и проверяет её инварианты.
2. Для поиска кандидатов репозиторий использует конструктивные и геометрические поля.
3. Entity-маппер восстанавливает найденные кандидаты в Domain; сервис сравнивает полные доменные конфигурации, включая физический состав оборудования.
4. При полном совпадении возвращается существующая конфигурация. Иначе создаётся новая Entity; сохранённая конфигурация по ID не обновляется.

# 8. БЕЗОПАСНОСТЬ И УПРАВЛЕНИЕ ПОЛЬЗОВАТЕЛЯМИ

## 8.1. Аутентификация и сессии

- **Механизм:** JWT (JSON Web Tokens). Учётная запись загружается из БД при обработке Access/Refresh JWT; статус активности проверяется на каждом запросе.
- **Текущая реализация:** Access и Refresh JWT устанавливаются в HTTP-only cookies. В проверенном коде генерации cookies явно не подтверждены атрибуты `Secure` и `SameSite`; фактические параметры указаны в разделе 13.5.
- **Целевое требование:** Для HTTPS-развёртывания cookies должны иметь `Secure`, `HttpOnly` и согласованную политику `SameSite`. Для cookie-based аутентификации должна быть включена CSRF-защита.
- **Истечение:** Сроки действия задаются конфигурацией приложения; конкретные значения не следует фиксировать в этом документе как универсальные.
- **Выход (Logout):** Текущая реализация очищает cookies. Серверный отзыв уже выданных JWT не подтверждён.

## 8.2. Управление паролями

- **Хеширование:** PasswordEncoder (BCrypt) с автоматической генерацией salt. Исходные пароли в БД не хранятся.
- **Смена пароля пользователем:** Доступна через /myprofile/changepassword. Требуется ввод нового пароля и его подтверждение.
- **Сброс пароля администратором:** Админ может принудительно сменить пароль любому сотруднику через /employees/{id}/changepassword.
- **Восстановление пароля (Forgot Password):** В текущей реализации отсутствует self-service восстановление через email. Корпоративная политика: пароль сбрасывает только администратор системы.

## 8.3. ⚠️ КРИТИЧЕСКОЕ ЗАМЕЧАНИЕ ПО РЕГИСТРАЦИИ

- В коде присутствует публичный эндпоинт POST /registration, который автоматически выдаёт роль ROLE_MANAGER любому зарегистрировавшемуся.
- **Требование для Production:** Полностью удалить или скрыть за флагом app.registration.enabled=false публичную регистрацию. Создание учётных записей должно осуществляться исключительно администратором через защищённый эндпоинт /employees/create.

## 8.4. Защита от атак

- **CSRF:** В текущей реализации CSRF-защита Spring Security отключена. Для целевой cookie-based аутентификации её необходимо включить и обеспечить передачу CSRF-токена в UI-формах и изменяющих состояние запросах. Нельзя считать CSRF-защиту действующей до проверки конфигурации и интеграционных тестов.
- **XSS:** Thymeleaf по умолчанию экранирует текст, выводимый через `th:text`; это не отменяет необходимости безопасной обработки HTML, URL и пользовательского содержимого в иных контекстах.
- **SQL Injection:** Использование параметризованных запросов Spring Data JPA снижает риск SQL-инъекций; динамические SQL-фрагменты, если они появятся, требуют отдельной проверки.
- **Авторизация:** Ограничения URL и методные аннотации могут применяться совместно. Фактическое наличие и полнота обоих уровней защиты проверяются по SecurityFilterChain и контроллерам.

# 9. ОБРАБОТКА ОШИБОК

## 9.1. Типы исключений

- **ValidationSizeException:** Нарушение ограничений размеров. Содержит ValidationResult. Перехватывается контроллером, пользователь возвращается на форму с подсветкой ошибок.
- **AuthException / IllegalArgumentException:** Ошибки аутентификации или несовпадения паролей. Отображаются как flash-сообщения (errorMessage).
- **AccessDeniedException:** Попытка доступа к ресурсу без прав. Возвращает HTTP 403 или редирект на главную.
- **DomainException (например, IllegalStateException):** Нарушение бизнес-инвариантов (например, отрицательная ширина ячейки).
- **EquipmentNotFoundException:** Оборудование не найдено в каталоге. Блокирует сохранение ALS с понятным сообщением.

## 9.2. Глобальный обработчик

Используется @ControllerAdvice для централизованной обработки необработанных исключений, логирования ошибок (SLF4J) и возврата пользовательских страниц ошибок (error.html).

## 9.3. Обработка ошибок в Draft-конфигураторе

При возникновении ошибки во время Find-or-Create:

- Транзакция откатывается полностью (не сохраняются частично созданные модули).
- DraftALS остаётся в HttpSession — пользователь не теряет введённые данные.
- Пользователь возвращается на форму с отображением ошибок.
- Пользователь может исправить параметры и повторить попытку.

# 10. ТРАНЗАКЦИОННОСТЬ И ИНДЕКСЫ БД

## 10.1. Границы транзакций

Аннотация @Transactional применяется на уровне Application Service (например, AuthService.createEmployee, ALSService.findOrCreate). Это гарантирует атомарность операций Find-or-Create: если создание связанного оборудования падает с ошибкой, вся транзакция откатывается, не оставляя "мусорных" записей.

## 10.2. Критические секции

**Find-or-Create** — критическая секция. Используется общая транзакционная блокировка строки `find_or_create_lock` с `SELECT ... FOR UPDATE`. В отличие от локального mutex приложения, блокировка БД координирует несколько экземпляров приложения и автоматически освобождается при завершении транзакции.

**Обновление ProjectALS** — атомарная операция замены ссылки на ALS.

## 10.3. Уровни изоляции

Для Find-or-Create не требуется повышать уровень изоляции до `SERIALIZABLE`: критическая секция защищена блокировкой выделенной строки InnoDB. Интеграционный тест `FindOrCreateLockIntegrationTest` проверяет, что вторая транзакция не получает блокировку до завершения первой. Гарантия действует при условии, что все операции создания конфигураций проходят через соответствующие сервисы.

## 10.4. Откат транзакций

При любом исключении внутри @Transactional — полный откат:

- Не сохраняются частично созданные модули.
- Не сохраняются частично созданные ALS.
- Draft в сессии остаётся (пользователь может исправить и повторить).

## 10.5. Индексы базы данных (целевые рекомендации)

Приведённые ниже индексы — предварительные примеры для проектирования Find-or-Create, а не утверждённая схема БД и не готовые миграции. Перед добавлением необходимо сверить имена таблиц и столбцов с JPA-сущностями, актуальными Flyway-миграциями, реальными запросами репозиториев и выбранной моделью идентичности конфигураций. Индексы должны ускорять реальные запросы и обеспечивать только согласованные ограничения уникальности.

    -- Оборудование
    CREATE INDEX idx_equipment_type_active ON equipment(equipment_type_id, is_active);
    CREATE INDEX idx_equipment_default ON equipment(equipment_type_id, is_default_for_type);

    -- Модули (для быстрого отсева кандидатов по габаритам)
    CREATE INDEX idx_module_dimensions ON module(module_type, height, width, depth);

    -- Связи ALS и Проектов
    CREATE INDEX idx_project_als_project ON project_als(project_id);
    CREATE INDEX idx_project_als_als ON project_als(als_id);
    CREATE UNIQUE INDEX uk_project_als ON project_als(project_id, als_id);

    -- Индекс ALS по характеристикам добавляется только после утверждения
    -- фактической схемы хранения и критериев Find-or-Create.

# 11. РАЗВЁРТЫВАНИЕ И КОНФИГУРАЦИЯ

## 11.1. Стенды

Используются два независимых стенда: DEV и TEST. Каждый размещается на отдельном ноутбуке и включает Docker Compose с MySQL, Kafka, `lb-calc-web` и `notification-service`. Данные MySQL и Kafka хранятся в отдельных Docker volumes.

Структура конфигурации одинакова:
```text
environments/
├── dev/
│   ├── .env
│   ├── .env.example
│   └── docker-compose.yml
└── test/
    ├── .env
    ├── .env.example
    └── docker-compose.yml
```

Один полный `.env` на стенд содержит настройки обоих приложений и инфраструктуры. Реальный файл не коммитится.

## 11.2. Единая адресация MySQL и Kafka

MySQL и Kafka запускаются только в Docker. Приложения можно запускать в Docker Compose или из IntelliJ IDEA; в обоих случаях они используют один адрес Docker-хоста и одинаковые опубликованные порты:
- MySQL: `DOCKER_HOST_ADDRESS:MYSQL_PORT`;
- Kafka: `DOCKER_HOST_ADDRESS:KAFKA_EXTERNAL_PORT`.

`DOCKER_HOST_ADDRESS` — LAN IP соответствующего ноутбука, закреплённый через DHCP reservation. Compose публикует порты MySQL и Kafka на адресе хоста; Kafka рекламирует клиентам тот же адрес. Контейнеры приложений не используют Docker DNS-имена `mysql` и `kafka`. Поэтому конфигурация приложения не меняется при переключении между IDEA и Docker.

## 11.3. Конфигурация приложений

- `lb-calc-web/src/main/resources/application.properties` содержит настройки основного приложения, MySQL, Kafka, JWT и логирования.
- `notification-service/src/main/resources/application.properties` содержит настройки HTTP-сервера и Kafka consumer.
- `size-bounds.properties` содержит доменные геометрические ограничения и не является конфигурацией стенда.
- Профиль Spring `test` и отдельный `application-test.properties` не используются.
- `notification-service` сохраняет HTTP-возможности и внутренний порт 8082.

Адрес MySQL формируется из `DOCKER_HOST_ADDRESS`, `MYSQL_PORT`, `MYSQL_DATABASE`; Kafka bootstrap servers — из `DOCKER_HOST_ADDRESS` и `KAFKA_EXTERNAL_PORT`. Эти параметры одинаковы для IDEA и Docker.

## 11.4. MySQL и Flyway

MySQL 8.4 запускается в отдельном контейнере каждого стенда. Для приложения создаётся отдельный пользователь БД; root-пароль используется только MySQL-контейнером. DEV и TEST имеют разные базы и volumes. Flyway применяет миграции при запуске `lb-calc-web`; Hibernate использует `ddl-auto=validate`.

## 11.5. Kafka

Kafka 4.0 запускается в режиме KRaft: один broker/controller на стенд. Topic пользовательских событий задаётся через `KAFKA_TOPIC_USER_EVENTS`; producer, consumer и создание topic используют единое свойство `app.kafka.topic.user-events`. Количество partitions задаётся параметром `KAFKA_TOPIC_USER_EVENTS_PARTITIONS` и применяется как к настройке автосоздания topic брокером, так и к явному созданию topic сервисом. Для одноброкерного стенда используются replication factor 1 и `min.insync.replicas=1`. Compose healthcheck проверяет готовность брокера, а приложения зависят от `service_healthy`.

## 11.6. Независимый запуск приложений

Оба приложения можно запускать независимо от инфраструктуры и друг от друга. Для запуска приложения из IntelliJ IDEA останавливается только его контейнер Compose; MySQL, Kafka и второе приложение продолжают работать. Для возврата приложения в Docker запускается соответствующий Compose service. IDEA получает переменные из `.env`; Compose передаёт контейнерам те же значения.

## 11.7. Docker и Java

Оба Dockerfile используют `eclipse-temurin:17-jre`, соответствующий целевой версии Java проекта. Внутренние HTTP-порты: `lb-calc-web` — 8081, `notification-service` — 8082.

## 11.8. Jenkins, CI/CD и версионирование

Jenkins размещён на DEV-ноутбуке. Используются две независимые Pipeline Job без отдельной Release Job. DEV запускается вручную с параметром SOURCE_BRANCH. TEST Pipeline содержит триггер Poll SCM с расписанием H/2 * * * *; Jenkins проверяет master каждые две минуты и запускает Pipeline при обнаружении нового commit:

- LB-CALC-DEV: Jenkinsfile infrastructure/Jenkinsfile.dev, Pipeline script from SCM берётся из refactor-main. При запуске задаётся SOURCE_BRANCH; разрешены feature/*, refactor/*, bugfix/*, а также временно refactor-main. Развёртывание выполняется на Docker Engine DEV.
- LB-CALC-TEST: Jenkinsfile infrastructure/Jenkinsfile.test, Pipeline script from SCM берётся из master. После merge PR в master выполняются вычисление релизной версии, сборка, создание Git-тега и развёртывание на Docker Engine TEST по SSH.

### Версионирование

Используется SemVer MAJOR.MINOR.PATCH. Каждый PR в master обязан иметь ровно одну GitHub-метку:

- version:patch — исправление ошибки без изменения публичного контракта;
- version:minor — новая обратно совместимая функциональность;
- version:major — несовместимое изменение.

GitHub Actions проверяет метку на PR. После merge TEST Pipeline получает PR, связанный с merge commit, и вычисляет следующую версию от последнего Git-тега vX.Y.Z. Для PATCH увеличивается PATCH, для MINOR — MINOR и обнуляется PATCH, для MAJOR — MAJOR и обнуляются MINOR/PATCH.

До появления первого Git-тега базой служит revision корневого POM без -SNAPSHOT (сейчас 0.1.0). Следовательно, первый merge с меткой PATCH создаст v0.1.1, MINOR — v0.2.0, MAJOR — v1.0.0.

После успешной сборки Jenkins создаёт аннотированный Git-тег и отправляет его в GitHub с использованием credential github-ssh. Повторный запуск для того же commit переиспользует уже созданный на нём тег, не увеличивая версию повторно. GitHub Releases не используются.

DEV использует последнюю версию из Git-тегов с суффиксом -SNAPSHOT; если тегов ещё нет — значение revision из корневого POM. Docker tag DEV включает версию, нормализованное имя ветки и BUILD_NUMBER; имя ветки ограничивается с учётом максимальной длины Docker tag (128 символов). Docker tag TEST включает релизную версию и BUILD_NUMBER. APP_VERSION и IMAGE_TAG передаются в Docker Compose из Jenkins и не хранятся в .env. При ручном локальном запуске Compose использует значения по умолчанию APP_VERSION=0.1.0-SNAPSHOT и IMAGE_TAG=local; перед этим JAR-файлы собираются Maven из корня проекта.

Оба Maven-модуля используют общую версию через корневое свойство revision; релизная версия передаётся сборке через -Drevision=.... Редактировать POM для каждого релиза не требуется.

### Разделение CI и deployment

GitHub Actions выполняет Maven verification и проверяет метку версии PR. Jenkins выполняет Docker build и deployment. DEV и TEST используют независимые Compose-файлы, .env, MySQL, Kafka и volumes. TEST Pipeline собирает JAR на Jenkins/DEV, передаёт их по SCP на TEST и запускает Compose на Docker Engine TEST. На TEST не нужны Java и Maven.

### Обязательные настройки GitHub и Jenkins

Для master необходимо включить защиту: PR-only, обязательный check Validate version label, запрет прямого push. Maven verification сделать обязательным после устранения ошибок интеграционных тестов. Создать GitHub labels version:patch, version:minor, version:major. На момент аудита master не защищена; эти настройки выполняются в GitHub Settings. Текущий Maven verification завершился 8 ошибками загрузки Spring ApplicationContext; до отдельного решения по интеграционным тестам этот check не включать в обязательные.

В Jenkins должны быть настроены:
- github-ssh — SSH credential с правом отправки тегов в GitHub;
- test-host-ssh — SSH credential для TEST;
- глобальные переменные TEST_HOST, TEST_PROJECT_DIR;
- DEV .env по /var/jenkins_env/dev/.env;
- TEST .env на TEST в environments/test/.env;
- host key TEST в /var/jenkins_home/.ssh/known_hosts.

TEST Pipeline находит PR через публичный GitHub API по merge commit; отдельный GitHub API token для чтения PR не требуется.


# 12. ГОСТЕВОЙ РЕЖИМ: ЛОКАЛЬНЫЕ ЧЕРНОВИКИ И ИМПОРТ ПРОЕКТОВ
## 12.1. Назначение гостевого режима

The application supports guest configuration without authentication. Guest projects are browser-local drafts; they are not persisted as Project records in MySQL. Guest mode changes the storage and authorization context, not the domain model or calculation rules.

## 12.2. Клиентское хранение

- IndexedDB stores guest projects and their complete configuration data.
- LocalStorage stores only lightweight UI preferences.
- The browser is responsible for retaining guest drafts until the user deletes them or successfully imports them into an account.
- The application must not treat browser storage as authoritative for catalog data or security decisions.

## 12.3. Доступ гостя к серверным данным

Guests may access explicitly public, read-only endpoints for equipment catalogs and reference data. Where authoritative calculations or validation are required, the application may expose narrowly scoped public endpoints that do not persist a guest Project.

All catalog mutations, administrative operations and account-specific project operations remain protected. No temporary guest-project database records, guest accounts or dedicated server-side guest sessions are created for draft storage.

## 12.4. Импорт после регистрации или аутентификации

1. The user registers or signs in.
2. The browser detects locally stored guest projects and offers the user a choice of which projects to import.
3. The browser submits selected project data to the authenticated REST API.
4. The server validates the submitted data through the shared Application Services and Domain Model. Client-side validation is only a usability aid and is not trusted.
5. The server assigns ownership using the authenticated principal, not a client-supplied owner identifier.
6. The server persists the project and returns a per-project success or failure result.
7. The browser deletes only those local projects for which successful persistence has been confirmed. Failed or unprocessed projects remain in IndexedDB.

## 12.5. MVC, REST и прикладные сервисы

MVC controllers render HTML/Thymeleaf; REST controllers accept and return JSON. Both expose the same business operations and call the same Application Services and Domain Model. They must not contain separate copies of project, ALS, equipment or calculation logic.

Guest and authenticated access is controlled at the security/application boundary. A public endpoint must not provide access to another user's saved projects or allow mutation of shared catalogs.

## 12.6. Требования к API и обработке ошибок

The import API must distinguish successful persistence from validation, authorization, conflict and infrastructure failures. A response must identify which submitted projects were successfully saved so that the client does not delete unsaved local data.

The agreed idempotency policy uses a persistent `guestProjectId` for each guest project. Repeating an import with the same `guestProjectId` returns the result of the original import and must not create a duplicate. Different `guestProjectId` values are not treated as duplicates solely because project names match. A similar existing project may trigger a warning, but must never be overwritten automatically. The browser removes a local project only after confirmed successful persistence; failed or indeterminate results leave the local copy intact.

| UI | Spring MVC + Thymeleaf |
| REST API | Существуют REST-контроллеры; фактические пути и контракты необходимо сверять с контроллерами |

| Деактивация/активация сотрудника | Реализована на persistence/security-уровне через `EmployeeEntity.active`, `EmployeePrincipal.isEnabled()` и административные сценарии; строка сотрудника не удаляется, ссылки проектов сохраняются |

## 13.2. Фактические доменные границы

Доменная модель не содержит самостоятельного агрегата Equipment и отдельного слоя resolver-сервисов для автоматического подбора и распределения оборудования. Конфигурации оборудования представлены доменными объектами и списками в `EquipmentConfiguration`.

`Project` хранит количество одинаковых ALS в `Map<ALS, Integer>`. Доменная операция `replaceALS()` уменьшает количество старой конфигурации на одну единицу и добавляет одну единицу новой конфигурации. Это соответствует сценарию редактирования выбранного экземпляра ALS.

`Project` использует `ALS` как ключ `Map`, а `equals()`/`hashCode()` ALS зависят от конфигурации. В текущей реализации риск изменения ключа ограничен инкапсуляцией: `Project` сохраняет независимые копии ALS, наружу возвращает копии ключей, а операции добавления, замены и восстановления также копируют конфигурации. Внутренние ключи не выдаются вызывающему коду для изменения. Это условие необходимо сохранять при дальнейших изменениях доменной модели.

## 13.3. Геометрический расчёт

Фактическая формула ширины ячейки в `StorageModule.recalculateStorageCells()`:

`cellWidth = moduleWidth - typeLb.deltaWidth - typeLb.serviceZoneWidth`.

Ширина сервисной зоны участвует в расчёте. Конструктивный тип разрешается application-слоем через `TypeLbFactory` из параметров приложения и передаётся в доменную модель как неизменяемый `TypeLb`. При выборе другого типа создаётся новая конфигурация LB/LBC; существующий объект не перенастраивается сеттером.

Остальные формулы и пределы следует сверять с `04-Бизнес-логика_и_состояние_реализации.md`, `SizeValidator` и `size-bounds.properties`.

## 13.4. Проектные и ALS-сценарии

Текущий сценарий сохранения проекта выполняется через `ProjectService` и `ALSService`. Проектные операции изменения состава и модулей загружают `Project` из `ProjectEntity` через `ProjectEntityMapper`, находят выбранную ALS внутри агрегата по persistence ID, создают независимую копию и выполняют изменения над ней в Domain. `Project.replaceALS()` уменьшает количество исходной конфигурации ровно на одну единицу и добавляет одну единицу новой конфигурации. Остальные экземпляры одинаковой ALS сохраняются.

`LBService.saveLB()`, `LCService.saveLC()`, `LBCService.saveLBC()` и `ALSService.saveALS()` реализуют Find-or-Create: совпадающая конфигурация переиспользует существующую запись, изменённая сохраняется как новая конфигурация. Входной ID LC/LBC используется только для проверки существования исходной записи и не приводит к обновлению её Entity. Старые конфигурации не обновляются на месте. `ProjectEntityMapper.updateEntity()` сохраняет существующие строки `ProjectALSEntity`, если соответствующая ALS остаётся в проекте, обновляет их количество, удаляет исчезнувшие связи и создаёт новые. ID связи Project–ALS не подменяется ID самой ALS.

`ProjectService.saveProject()` восстанавливает доменный `Project` из копии входного DTO с помощью `ALSService.restoreDomain()`; конструктивные параметры LB/LBC разрешаются через `TypeLbFactory`, а историческое оборудование — через resolver исходной комплектации. Проектные операции редактирования загружают агрегат из `ProjectEntity` и работают с ним без промежуточного преобразования в DTO. Оба сценария после проверки прав и доменной валидации используют общий `persistProject()`: каждая уникальная ALS из `Project.getQuantityALS()` сохраняется через `ALSService.saveALS(ALS)`, затем разрешается в `ALSEntity` по ID и агрегат преобразуется в `ProjectEntity`. Входной `ProjectDTO` не изменяется: серверные metadata устанавливаются на его копии. Для доменных операций метаданные обновляются на самом агрегате перед вызовом общего сохранения.

Полиморфное преобразование модулей между `Module` и `ModuleEntity` выполняет `ModuleEntityMapper`, который делегирует преобразование конкретных типов специализированным мапперам LB, LC и LBC. `ALSEntityMapper` отвечает за агрегат ALS и сохраняет физический порядок модулей через `ALSModuleEntity.moduleOrder`.

Состав оборудования LC/LBC хранится единообразно как набор каталожных позиций с количеством каждой позиции. Entity-мапперы восстанавливают доменную `EquipmentConfiguration` по идентификаторам каталога; группы required/additional в persistence не разделяются, поскольку доменное равенство определяется физическим составом оборудования без учёта группы. Find-or-Create использует геометрические и конструктивные параметры для выборки кандидатов, после чего выполняет полное сравнение восстановленных доменных конфигураций.

При восстановлении редактируемой конфигурации прикладной сервис получает сохранённый управляющий модуль и resolver каталога, сохраняет ранее выбранные позиции и формирует итоговый список `EquipmentSelectionDTO`. Подготовленный список передаётся в DTO-маппер отдельным аргументом. Входящие DTO не изменяются: сервис не записывает восстановленный состав обратно через `setEquipmentSelections()`. Методы `ALSService.restoreDomain()`, `restoreLC()` и `restoreLBC()` координируют получение данных и применение `EquipmentRequirementResolver`; преобразование полей и структуры выполняют DTO-мапперы, не обращающиеся к репозиториям. При восстановлении LC/LBC из уже загруженной Domain-модели ALS контекст исходной комплектации определяется напрямую по ID ALS и управляющего модуля; обратное преобразование Domain → DTO только для поиска Entity не используется. При замене управляющего модуля уже восстановленная доменная ALS не пересоздаётся из DTO: новый LC/LBC восстанавливается отдельно на основе сохранённого модуля, входящего в исходную ALS. Для каждой такой операции используется `EquipmentRestoreContext` с `findExistingConfigurationResolver(retainedIds)`; деактивированные позиции разрешаются только если они уже входили в исходную сохранённую комплектацию. Если `equipmentSelections == null`, сохранённые позиции объединяются с новым выбором дисплея; явно переданный пустой список не трактуется как null. При замене существующего LBC новым шаблоном ID исходного модуля используется для восстановления сохранённой комплектации: дополнительное оборудование сохраняется, а выбор дисплея берётся из нового шаблона.

DTO сохраняет физический порядок модулей через `moduleOrder` — упорядоченный список ссылок на элементы `lbList` и единственный управляющий модуль LC/LBC. При обратном преобразовании маппер проверяет полноту ссылок, отсутствие повторов и соответствие производного `positionControlModule` физическому порядку. Для старых клиентов, не передающих `moduleOrder`, сохраняется совместимый путь восстановления порядка по LEFT/RIGHT/CENTER с балансировкой сторон.

Количество ALS изменяется доменными операциями по одной единице: `addALS()`, `removeALS()`, `replaceALS()`. Редактирование выбранной конфигурации через `ProjectService.replaceALSandSaveProject()` уменьшает количество старой конфигурации на одну и добавляет одну единицу новой. Если одинаковых ALS несколько, остальные сохраняются. `ProjectEntityMapper.updateEntity()` сохраняет существующую строку связи Project–ALS и её ID, пока соответствующая конфигурация остаётся в проекте; для новой конфигурации создаёт новую строку связи.

## 13.5. Безопасность и доступ к проектам

Чтение проектов не ограничивается владельцем: `findAll()` и `findById()` доступны аутентифицированным сотрудникам, что соответствует правилу «менеджер видит все проекты». Для изменения и удаления действует проверка в `ProjectService`: администратор может изменять любой проект, менеджер — только проект, где он указан как `createdBy`. Сценарии редактирования состава ALS и модулей проходят через доменный путь сохранения `saveDomainProject()`, который повторно проверяет право изменения проекта и сохраняет изменения в рамках транзакции.

CSRF отключён. Cookie JWT в проверенном коде устанавливаются с HttpOnly и Path=/; явная установка Secure и SameSite в коде генерации не подтверждена. Эти особенности фиксируют состояние реализации, но не являются рекомендацией по безопасности.

# 14. СОГЛАСОВАННАЯ ЦЕЛЕВАЯ МОДЕЛЬ ДОМЕНА

Этот раздел фиксирует архитектурно значимые бизнес-решения, которые должны учитываться при дальнейшем проектировании и реализации. Он не утверждает, что соответствующая функциональность уже присутствует в коде. При расхождении целевой модели с фактической реализацией приоритет имеет целевое правило из DDD, Business Logic и ТЗ, а факт реализации описывается отдельно.

1. Project агрегирует одинаковые ALS по количеству. Редактирование выбранного экземпляра ALS затрагивает только одну единицу и выполняется через глубокую независимую копию; исходная общая конфигурация и другие проекты не меняются.
2. Единственный источник физического порядка — упорядоченный список модулей ALS. Положение LC/LBC вычисляется по индексу. Правила LEFT/CENTER/RIGHT одинаковы для LC и LBC; для одиночного LBC технически допускается нейтральный CENTER, не отображаемый как физическая позиция.
3. Направления дверей обычных LB вычисляются относительно управляющего модуля. Для LBC действует отдельное правило: LEFT → RIGHT, CENTER → LEFT, RIGHT → LEFT.
4. При CENTER новые LB распределяются по обе стороны управляющего модуля так, чтобы разница между количеством LB слева и справа не превышала одного. Новый LB добавляется на менее заполненную сторону; если количество одинаково, допустима любая сторона.
5. EquipmentConfiguration входит в LC/LBC. FunctionalSelection является временным состоянием выбора способов доступа и оплаты, а не самостоятельной сохраняемой доменной сущностью. PrintOption не используется как независимый сохраняемый выбор; необходимость принтера выводится из функциональных требований.
6. Функциональный резолвер не формирует базовую комплектацию и не управляет LOCK_CONTROLLER, COMPUTER, POWER_SUPPLY и UPS. При выборе или изменении функциональности система немедленно подбирает и показывает конкретные модели оборудования. RFID требует RFID-считыватель; BARCODE — считыватель штрихкодов; QR — считыватель с поддержкой 2D; PIN — дисплей 10/17/19 дюймов и минимум один дополнительный способ доступа (RFID/BARCODE/QR). CASHLESS требует PAYMENT_TERMINAL; CASH_AND_CARDS требует PAYMENT_TERMINAL и CASH_ACCEPTOR. Принтер обязателен при ненулевой оплате либо при BARCODE, QR или PIN.
7. Пользователь может заменить предложенную модель на другую активную совместимую модель. Отдельного признака ручного закрепления оборудования нет; при изменении функциональности больше не требуемое оборудование удаляется, а необходимое другим функциям сохраняется. Один общий компонент устанавливается один раз.
8. Для каждого требования/категории каталога допускается ровно одна активная модель по умолчанию. Деактивированная модель остаётся в ранее сохранённых конфигурациях и может быть оставлена без изменений при их редактировании, но недоступна для повторного выбора/добавления и для новых конфигураций.
9. Идентичность позиции оборудования в комплектации определяется каталожным ID; количество хранится отдельно. Порядок оборудования не влияет на идентичность комплектации.
10. Сохранённые конфигурации неизменяемы по бизнес-полям. Изменение выполняется через Find-or-Create и замену ссылки в проекте.
11. Геометрия, общие параметры ALS, полная валидация, названия и описания должны соответствовать целевым формулам и правилам в DDD и Business Logic.
12. Employee остаётся доменной моделью сотрудника; отдельный UserAccount не вводится. Удаление сотрудника заменяется деактивацией, сохраняющей авторство и блокирующей авторизацию.
13. Гостевой импорт использует постоянный guestProjectId для идемпотентности; локальная копия удаляется только после подтверждённого успешного сохранения.

Незакрытых предметных вопросов, блокирующих текущий этап проектирования, нет. Физические электронные замки (`ELECTRONIC_LOCK`), их количество и правила распределения по ячейкам остаются отдельной будущей доработкой.

## 13.8. Сохранение производных характеристик в JPA

В `refactor-main` производные характеристики доменных конфигураций сохраняются вместе с исходными параметрами:

- `ProjectEntity.description`;
- `ALSEntity.name`, `description`, `width`;
- `ModuleEntity.name`, `description`;
- `StorageModuleEntity.heightCell`, `widthCell`, `depthCell`.

Единственным источником формул и правил остаётся Domain. Entity Mapper переносит рассчитанные значения в JPA-сущности. При восстановлении Domain мапперы заново рассчитывают характеристики и сравнивают их с сохранённым снимком. Несоответствие считается нарушением целостности данных и приводит к `IllegalStateException`. Геометрические формулы в Entity не дублируются.

Номера ячеек не сохраняются в общей конфигурации модуля: они назначаются агрегатом ALS в зависимости от физического порядка модулей.

`ALSEntityMapper` синхронизирует связи `ALSModuleEntity`: неизменившиеся пары «модуль + позиция» переиспользуются, изменившиеся связи заменяются. Это сохраняет стабильные association entities и не требует перестановки значений уникального индекса `(als_id, module_order)`.

Начальная миграция Flyway V1 создаёт схему под актуальные JPA-сущности, включая производные характеристики и `employee.is_active`. Hibernate работает в режиме `ddl-auto=validate`. Соответствие схемы фактическим mappings должно подтверждаться запуском на чистой MySQL; само наличие DDL и аннотаций не заменяет интеграционную проверку.
### Пакетная загрузка при чтении конфигураций

- Для преобразования LC/LBC/ALS/Project из persistence-моделей используется единый снимок каталога оборудования на операцию чтения или сохранения, а не отдельный запрос на каждую позицию.
- При редактировании существующей конфигурации разрешитель допускает деактивированные позиции только из исходного состава; новые позиции должны быть активны.
- Коллекции оборудования LC/LBC и связи агрегатов ALS/Project загружаются пакетами Hibernate (`@BatchSize(size = 50)`), чтобы сократить N+1 при выдаче списков проектов и конфигураций.
- Пакетная загрузка не заменяет транзакционные границы: операции преобразования сущностей с ленивыми связями выполняются внутри сервисных транзакций.
- Единственность активной модели по умолчанию контролируется сервисом; миграция V4 дополнительно обеспечивает уникальность на уровне MySQL через generated column `active_default_category` и уникальный индекс.
