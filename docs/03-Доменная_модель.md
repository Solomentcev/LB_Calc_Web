# Доменная модель LB_Calc_Web

**Назначение документа:** описание предметной области и доменной модели LB_Calc_Web с разграничением фактически реализованной модели и согласованной целевой семантики.

**Область фактического описания:** ветка `refactor-main`.

**Структура документа:**
- разделы 1–9 описывают доменные типы, их фактическое поведение и ограничения реализации;
- раздел 10 фиксирует согласованные целевые предметные правила, которые должны учитываться при развитии доменной модели.

> Наличие класса в доменном пакете не означает, что все операции приложения уже выполняются через него. Целевые правила раздела 10 не следует считать реализованными без проверки кода.

## 1. Назначение предметной области

LB_Calc_Web предназначен для проектирования автоматизированных камер хранения (АКХ), формирования их конфигураций, расчёта геометрических параметров и подготовки представления конструкции.

Основные понятия предметной области:

- **Проект** — набор конфигураций АКХ, включённых в проект, с количеством каждой конфигурации.
- **ALS** — конфигурация автоматизированной системы хранения, состоящая из модулей в физическом порядке слева направо.
- **Модуль** — конструктивная часть ALS. В модели представлены модули хранения LB, управления LC и комбинированный LBC.
- **Ячейка хранения** — элемент модуля хранения, для которого рассчитываются размеры и назначается номер в составе ALS.
- **Конфигурация управления** — набор функций управления, способов доступа, вариантов печати и оборудования.
- **Оборудование** — устройства, используемые в конфигурациях модулей.
- **Сотрудник** — доменное представление сотрудника приложения с персональными данными и ролью.

## 2. Границы доменной модели

Основные доменные классы находятся в пакете:

`com.lb_calc_web.domain`

В модели выделены следующие группы:

| Группа | Основные типы | Назначение |
|---|---|---|
| Модели | `Project`, `ALS`, `Module`, `LB`, `LC`, `LBC`, `Employee` | Представление предметных объектов и их поведения |
| Конструктивные модели | `StorageModule`, `StorageCell`, `ControlModule` | Общая логика модулей хранения и управления |
| Конфигурации | `ControlConfiguration`, `EquipmentConfiguration` | Параметры функций управления и состав оборудования |
| Оборудование | `Equipment`, специализированные типы оборудования | Представление устройств |
| Атрибуты | `Colors`, `TypeLb`, `Payment`, `AccessMethod`, `PrintOption`, `DirectionDoorOpening`, `PositionControlModule`, `Role` | Значения и характеристики предметной области |

Доменная модель не содержит JPA-аннотаций и не обращается напрямую к Spring Data Repository. Идентификаторы БД и преобразования между доменом, DTO и JPA-сущностями находятся за пределами доменных объектов.

## 3. Доменная модель

### 3.1. Project

`Project` представляет проект и управляет его составом.

Основные атрибуты:

- `name` — название;
- `description` — автоматически формируемое описание состава;
- `company` — компания;
- `createdAt`, `updatedAt` — даты создания и изменения;
- `createdBy`, `updatedBy` — сотрудники;
- `quantityALS` — карта конфигураций ALS и их количества.

Состав хранится в виде `Map<ALS, Integer>`. Одна запись карты означает одну конфигурацию ALS и количество её экземпляров в проекте. Это доменное представление не содержит отдельного объекта для каждой физической копии одинаковой конфигурации.

Основные операции:

- `addALS(ALS)` — добавить одну единицу; если равная конфигурация уже есть, увеличить её количество;
- `removeALS(ALS)` — удалить одну единицу; при достижении нуля удалить конфигурацию из состава;
- `replaceALS(oldALS, newALS)` — заменить конфигурацию с переносом всего её текущего количества;
- `getQuantity(ALS)` — получить количество;
- `restore(...)` — восстановить проект из сохранённых данных без регистрации восстановления как нового изменения.

Изменение состава обновляет дату изменения и автоматически пересчитывает описание. `getQuantityALS()` возвращает карту только для чтения.

**Важное ограничение текущей реализации:** `replaceALS()` переносит всё количество старой конфигурации, а не одну единицу. Поэтому этот метод не реализует согласованное правило редактирования одного экземпляра ALS.

**Технический риск:** ALS используется как ключ изменяемой карты. При этом `ALS.equals()` и `hashCode()` зависят от конфигурации модулей, а сама ALS и её модули могут пересчитываться и изменяться. Изменение ключа после помещения в HashMap/LinkedHashMap может нарушить корректность поиска по ключу. Это зафиксированное ограничение реализации, а не допустимое бизнес-правило.

### 3.2. ALS

`ALS` — агрегат конструкции, объединяющий модули в физическом порядке слева направо.

Основные атрибуты:

- автоматически формируемые `name` и `description`;
- `height`, `width`, `depth`;
- `upperFrame`, `bottomFrame`;
- `colorBody`, `colorDoor`;
- упорядоченный список `modules`.

Список модулей — единственный источник истины для физического порядка. Положение модуля управления, направления открытия дверей, нумерация ячеек и общая ширина являются производными характеристиками.

Структурные инварианты:

1. В ALS должен находиться ровно один объект, реализующий `ControlModule`.
2. В ALS должен находиться хотя бы один объект, реализующий `StorageModule`.
3. Один объект LBC может одновременно выполнять роли `ControlModule` и `StorageModule`.
4. Порядок элементов списка определяет расположение модулей слева направо.

Основные операции:

- добавление модуля в конец или в указанную позицию;
- удаление конкретного экземпляра модуля по идентичности объекта;
- получение управляющего модуля и списка модулей хранения;
- получение общего количества ячеек;
- определение положения управляющего модуля;
- полный пересчёт производных характеристик.

Удаление модуля выполняется по идентичности (`==`), а не по `equals()`. Это позволяет различать два отдельных экземпляра одинаковой конфигурации модуля.

### 3.3. Module

`Module` — абстрактная базовая модель модуля.

Общие характеристики:

- название и описание;
- высота, ширина и глубина;
- размеры верхней и нижней рам;
- цвет корпуса и дверей.

Каждый конкретный модуль реализует `recalculate()`, пересчитывающий его производные параметры.

### 3.4. StorageModule и StorageCell

`StorageModule` — базовый класс модулей, содержащих ячейки хранения. Он хранит:

- конструктивный тип `TypeLb`;
- направление открытия дверей;
- список `StorageCell`;
- рассчитанные высоту, ширину и глубину ячейки;
- толщину дверцы, используемую при расчёте глубины.

Количество ячеек определяется размером списка объектов `StorageCell`, а не отдельным независимым счётчиком. Вызов `setCountCells()` создаёт новый список ячеек заданного размера и запускает пересчёт; отдельная идентичность/ID ячейки в доменной модели отсутствует. Номер ячейки назначается позднее агрегатом ALS.

Номера ячеек не являются частью самостоятельной конфигурации модуля. Их назначает ALS с учётом положения модуля в общей конструкции. При копировании LB/LBC создаются новые объекты ячеек без переноса их номеров; ALS назначает номера заново при пересчёте агрегата.

Размеры ячейки рассчитываются в `StorageModule`:

- ширина ячейки = ширина модуля − `TypeLb.deltaWidth` − `TypeLb.serviceZoneWidth`;
- глубина ячейки = глубина модуля − толщина дверцы;
- полезная высота = высота модуля − верхняя рама − нижняя рама − суммарная толщина полок между ячейками;
- высота ячейки = целая часть от деления полезной высоты на количество ячеек.

Высота рассчитывается целочисленным делением, дробная часть отбрасывается без округления. При нулевом количестве ячеек высота ячейки равна нулю; отсутствие конструктивного типа приводит к исключению.

### 3.5. LB

`LB` — модуль хранения. Содержит конструктивные параметры, тип LB, направление открытия дверей и набор ячеек.

При пересчёте LB рассчитывает размеры ячеек, формирует наименование и описание. Сравнение конфигураций LB выполняется по исходным конструктивным параметрам; производные название, описание, размеры ячеек и номера ячеек не являются самостоятельными параметрами идентичности.

### 3.6. LC

`LC` — модуль управления. Он реализует интерфейс `ControlModule` и содержит конфигурацию управления и оборудование.

В конфигурации управления представлены способ оплаты, способы доступа, варианты печати и состав оборудования. LC не является модулем хранения и не содержит ячеек.

### 3.7. LBC

`LBC` — комбинированный модуль. Он совмещает функции модуля хранения и модуля управления, поэтому участвует в ALS одновременно как `StorageModule` и `ControlModule`.

Следствия:

- LBC учитывается как единственный модуль управления ALS;
- LBC также учитывается при подсчёте модулей хранения и ячеек;
- для направления открытия дверей LBC применяется отдельное правило, отличающееся от обычного LB.

### 3.8. ControlConfiguration

`ControlConfiguration` описывает функциональную конфигурацию управления:

- `Payment` — способ оплаты;
- `AccessMethod` — множество способов доступа;
- `PrintOption` — множество вариантов печати;
- `EquipmentConfiguration` — состав оборудования.

Способы доступа и варианты печати хранятся как множества: порядок их элементов не имеет предметного значения. При создании наборы копируются в независимые EnumSet, наружу возвращаются представления только для чтения. Конфигурация оборудования также копируется при создании и выдаче из `ControlConfiguration`; позиции `Equipment` неизменяемы, поэтому копирование состава создаёт независимые коллекции и количества без клонирования самих позиций каталога.

### 3.9. EquipmentConfiguration

`EquipmentConfiguration` разделяет позиции оборудования на обязательные и дополнительные. Внутри каждой группы хранится соответствие каталожной позиции её количеству (`Map<Equipment, Integer>`). Повторное добавление одной позиции увеличивает количество, а не создаёт вторую независимую позицию. Количество дисплеев ограничено одной единицей.

Наружу возвращаются неизменяемые списки уникальных позиций и отдельные значения `EquipmentItem`, содержащие позицию и количество. Изменение выполняется доменными методами добавления и удаления. При сравнении учитываются идентификаторы позиций и их количество; порядок элементов и принадлежность к обязательной/дополнительной группе не меняют физическую идентичность комплектации. Разделение на группы используется для правил изменения конфигурации.

### 3.10. Equipment

`Equipment` — базовая абстракция каталожной позиции оборудования. Она содержит стабильный `catalogPositionId` и отображаемое наименование. Количество не является частью объекта оборудования и хранится в `EquipmentConfiguration`.

Конкретные характеристики зависят от типа оборудования. Не следует трактовать базовый класс как утверждение, что все устройства имеют одинаковый набор характеристик.

### 3.11. Employee и Role

`Employee` — доменная модель сотрудника приложения. В ней представлены только предметные данные:

- `firstName` — имя;
- `lastName` — фамилия;
- `email` — адрес электронной почты;
- `registrationDate` — дата регистрации;
- `role` — роль сотрудника.

Конструктор требует ненулевые значения всех пяти атрибутов. Изменение доменного состояния явно представлено методом `changeRole(Role)`. Отдельных доменных методов изменения имени, фамилии или email в текущей модели нет. `Employee` не переопределяет `equals()` и `hashCode()`, поэтому сравнение экземпляров выполняется по ссылочной идентичности. Отдельного доменного класса `User` в текущей модели нет: сохранённая `EmployeeEntity` одновременно содержит данные сотрудника и учётные данные для входа.

`Role` содержит два значения:

- `ROLE_ADMIN` — административная роль;
- `ROLE_MANAGER` — роль менеджера.

Роль — доменный атрибут сотрудника, но фактические полномочия определяются не одним enum, а конфигурацией Spring Security и ограничениями контроллеров.

**Граница доменной модели:** `Employee` не содержит persistence ID, пароль/хэш пароля, JWT, признак активности или блокировки. Эти данные находятся в `EmployeeEntity` и security-слое. `EmployeeEntityMapper` намеренно не переносит ID и хэш пароля при преобразовании в домен и обратно.

### 3.12. Значения и конструктивные атрибуты

В предметной модели используются следующие типы значений:

| Тип | Представленные значения / данные | Назначение |
|---|---|---|
| `Payment` | `NONE`, `CASHLESS`, `CASH_AND_CARDS` | Вариант оплаты |
| `AccessMethod` | `PIN`, `QR_CODE`, `BARCODE`, `RFID` | Способы доступа |
| `PrintOption` | `PIN`, `QR_CODE`, `BARCODE` | Варианты печати |
| `DirectionDoorOpening` | `LEFT`, `RIGHT` | Направление открытия дверей |
| `PositionControlModule` | `LEFT`, `CENTER`, `RIGHT` | Положение управляющего модуля |
| `Colors` | Black, Blue, Cyan, DarkGray, Gray, Green, LightGray, Magenta, Orange, Pink, Red, White, Yellow | Цвет корпуса и дверей |
| `TypeLb` | Наименование типа, добавочная ширина, толщина полки, ширина сервисной зоны | Конструктивные параметры модуля хранения |

`TypeLb` — не enum, а отдельный неизменяемый объект со значениями `type`, `deltaWidth`, `shelfThick` и `serviceZoneWidth`. Его конструктор запрещает пустое наименование и отрицательные размеры. Равенство определяется всеми четырьмя полями. Значения поступают из конфигурации приложения через `TypeLbFactory` application-слоя. При создании доменной модели LB/LBC сервис разрешает выбранное имя типа в полный объект `TypeLb`; DTO не является источником конструктивных размеров. Смена типа означает создание новой конфигурации модуля с новым `TypeLb`, а не изменение уже созданного объекта через сеттер. Для LBC допускается использование параметров соответствующего типа LB, если отдельные параметры LBC не заданы.

В коде также присутствует `PositionLC` с теми же значениями положения. Наличие этого enum само по себе не доказывает, что он используется как отдельное бизнес-понятие: фактическое применение следует определять по конкретным местам использования.

### 3.13. Модель оборудования

Базовый `Equipment` задаёт стабильный `catalogPositionId`, отображаемое название и контракт получения ширины, высоты, глубины и описания. Идентификатор и название обязательны.

Равенство оборудования реализовано финальными `equals()` и `hashCode()` только по `catalogPositionId`. Название, конкретный Java-класс и количество не определяют идентичность позиции. Количество задаётся отдельно объектом `EquipmentItem` и учитывается в идентичности комплектации.

В текущем домене представлены:

- `Display`: варианты `NONE`, `LC10`, `LC17`, `LC19`; для них заданы размеры дисплея и минимальная ширина модуля;
- `Printer`: принтер;
- `RfidReader`: RFID-считыватель;
- `BarReader`: варианты `NONE`, `READER_1D`, `READER_2D`.

Для принтера, RFID-считывателя и сканеров текущие реализации возвращают нулевые габариты. Это характеристика имеющейся модели, а не утверждение об отсутствии физических размеров устройств.

Поддерживаемые позиции перечислены в кодовом каталоге `EquipmentCatalog`; их строковые идентификаторы являются стабильными ключами. Отдельная JPA-сущность и CRUD-управление каталогом пока не введены. В persistence-модели LC/LBC идентификаторы дисплея и сканера сохраняются в соответствующих строковых полях, количество оборудования — в отдельных числовых полях. Для принтера и RFID-считывателя позиция однозначно задаётся их стабильным идентификатором в доменной модели и специализированным полем persistence-модели.

### 3.14. Состав конфигурации управления и оборудования

`ControlConfiguration` объединяет один вариант оплаты, множество способов доступа, множество вариантов печати и `EquipmentConfiguration`.

Для множеств способов доступа и печати:

- порядок элементов не имеет значения;
- при создании формируются независимые `EnumSet`;
- наружу возвращаются представления только для чтения.

`EquipmentConfiguration` разделяет позиции на обязательные и дополнительные группы. В каждой группе позиция хранится один раз, количество ведётся отдельно. Сравнение комплектаций не зависит от порядка позиций и их распределения по группам, но учитывает каталожные ID и количество.

Само наличие обязательного и дополнительного списков не определяет алгоритм подбора, совместимости или размещения оборудования. Такие правила должны описываться отдельно только в той мере, в какой они подтверждены фактической реализацией.



**Особенности пересчёта конкретных модулей:**

- `LB.recalculate()` пересчитывает ячейки и формирует производные имя/описание модуля хранения.
- `LC.recalculate()` формирует производные имя и описание на основании геометрии и конфигурации управления. Минимальная ширина, необходимая для установленного оборудования, проверяется `ModuleSizeValidator`.
- `LBC.recalculate()` пересчитывает ячейки хранения и формирует производные имя/описание комбинированного модуля. Описание включает как storage-, так и control-конфигурацию.
- Общая текстовая часть конфигурации управления формируется методом `ControlModule.getControlDescription()` и используется как LC, так и LBC. Изменение оборудования или параметров управления запускает пересчёт описания.
- `getEquipmentHeight()` у LC и LBC возвращает максимальную высоту среди установленного оборудования либо 0, если оборудование отсутствует.

## 4. Пересчёт ALS

Метод `ALS.recalculate()` выполняет последовательность:

1. Проверяет структурные инварианты ALS.
2. Передаёт общие параметры ALS всем модулям: высоту, глубину, размеры рам и цвета.
3. Рассчитывает направления открытия дверей модулей хранения с учётом положения управляющего модуля.
4. Вызывает пересчёт каждого модуля.
5. Перенумеровывает ячейки в порядке обхода модулей.
6. Рассчитывает общую ширину как сумму ширин модулей.
7. Обновляет наименование и описание ALS.

Положение управляющего модуля определяется индексом control-модуля в списке:

- индекс 0 — LEFT;
- последний индекс — RIGHT;
- промежуточный индекс — CENTER;
- ALS из одного LBC рассматривается как CENTER.

Для обычных модулей хранения направление открытия дверей определяется относительно положения control-модуля. Для LBC применяется отдельная ветвь правила.

## 5. Сравнение конфигураций

В доменной модели `equals()` используется для сравнения конфигураций модулей и ALS, а не для сравнения persistence-записей.

- ALS сравнивается по общим конструктивным параметрам и упорядоченному списку модулей.
- Порядок модулей имеет значение.
- Производные ширина, имя, описание и положение control-модуля отдельно не сравниваются.
- Модули сравниваются по исходным параметрам соответствующего типа.
- Для удаления конкретного модуля используется идентичность объекта, а не равенство конфигураций.

Поскольку часть сравниваемых объектов изменяема, применение доменных объектов в качестве ключей хеш-коллекций требует отдельного контроля жизненного цикла ключа.

## 6. Доменная модель и JPA-модель

Доменная модель не совпадает один к одному со структурой таблиц.

| JPA-сущность | Назначение |
|---|---|
| `ProjectEntity` | Сохранённый проект |
| `ProjectALSEntity` | Связь проекта с конфигурацией ALS и количество этой конфигурации |
| `ALSEntity` | Сохранённая конфигурация ALS |
| `ALSModuleEntity` | Связь ALS с модулем и его порядком |
| `ModuleEntity` | Сохранённая конфигурация модуля и её специализированные реализации |
| `EmployeeEntity` | Сохранённые данные сотрудника/учётной записи |

Ключевые различия:

- `ProjectALSEntity.id` — идентификатор связи, не идентификатор ALS.
- `ALSEntity.id` — идентификатор сохранённой конфигурации ALS.
- `ProjectALSEntity.quantity` — количество данной конфигурации в конкретном проекте.
- `ALSModuleEntity.id` — идентификатор связи модуля с ALS.
- `ModuleEntity.id` — идентификатор сохранённой конфигурации модуля.

Одна запись `ALSEntity` может быть связана с несколькими проектами через `ProjectALSEntity`. Поэтому изменение общей записи ALS затрагивает все проекты, ссылающиеся на неё.

Связь ALS с модулями организована через `ALSModuleEntity`. Порядок модулей хранится в связи. `ALSEntity` удаляет свои связи с модулями каскадно и через orphan removal; сама конфигурация `ModuleEntity` не является дочерней записью ALS и не должна удаляться только из-за удаления связи.

## 7. Повторное использование конфигураций

Сервисы модулей и ALS используют поиск совпадающих конфигураций перед созданием новой записи. Для модулей `ALSService.resolveModule()` сравнивает доменную конфигурацию с преобразованными из существующих `ModuleEntity` объектами и переиспользует найденную запись. При отсутствии совпадения создаётся новая.

Повторное использование сохранённой конфигурации не означает, что один изменяемый доменный экземпляр должен совместно использоваться несколькими независимыми операциями редактирования. Следует различать:
- повторное использование неизменяемой/неизменяемой в рамках операции записи конфигурации в хранилище;
- совместное использование изменяемого объекта в памяти;
- связь нескольких проектов с одной записью `ALSEntity`.

## 8. Границы реализации и механизмы, которые нельзя приписывать домену

В текущем коде не подтверждены как реализованные именно на доменном уровне:

- публикация доменных событий агрегатами `Project`, `ALS`, `Employee`;
- отдельные доменные сервисы для разрешения требований и распределения оборудования;
- универсальный агрегат оборудования с единым управляемым каталогом всех типов;
- полная неизменяемость ALS и модулей после сохранения;
- отдельный серверный Draft-агрегат ALS;
- гарантированная независимость редактируемой ALS от других проектов, использующих ту же запись `ALSEntity`.

При этом в приложении **реализована отдельная интеграция пользовательских событий через Kafka**: `AuthService` формирует `UserEvent` и отправляет его через `KafkaTemplate`, а отдельный `notification-service` содержит Kafka consumer. Это прикладная интеграция, инициируемая сервисом, а не механизм доменных событий внутри агрегатов.

Наличие интеграционных событий не означает, что все значения `UserEventType` уже публикуются или что фактически отправляется email: текущее состояние описано в документе «Бизнес-логика LB_Calc_Web».

## 10. Согласованные предметные правила и целевая семантика домена

Этот раздел является нормативным описанием согласованной целевой модели. Он имеет приоритет над формулировками выше, описывающими только текущее состояние кода. Текущее состояние и расхождения реализации фиксируются отдельно в документе «Бизнес-логика LB_Calc_Web».

### 10.1. Проект и состав ALS

- Доменный `Project` представляет состав через `Map<ALS, Integer> quantityALS`: одинаковые конфигурации ALS агрегируются в одну запись с количеством.
- Порядок ALS внутри проекта не имеет предметного значения.
- DTO может передавать физический состав списком `alsList`; количество одинаковых ALS вычисляется при преобразовании в домен. `quantityALS` не является вторым независимым источником данных.
- В persistence количество хранится в связи Project–ALS. Идентификатор связи проекта с ALS и идентификатор самой конфигурации ALS — разные идентификаторы.
- Редактирование выбранного экземпляра ALS изменяет ровно одну единицу количества. Например, из трёх одинаковых ALS после редактирования одной остаются две исходные и появляется одна новая конфигурация.
- Изменение одной ALS не должно менять конфигурацию, используемую другими проектами.
- Сценарий редактирования получает ALS именно из состава выбранного проекта, создаёт глубокую независимую копию, применяет изменения и заменяет одну единицу в Project. Нельзя повторно загружать глобальную конфигурацию вместо экземпляра, выбранного в проекте.
- Массовое редактирование всех одинаковых экземпляров — отдельный сценарий.
- Равные сохранённые конфигурации модулей можно переиспользовать, если это не приводит к совместному изменению изменяемого состояния.

### 10.2. Состав ALS и роли модулей

- `LB` — модуль хранения.
- `LC` — модуль управления.
- `LBC` — один физический комбинированный модуль, одновременно выполняющий роли хранения и управления. LBC не раскладывается на два физических модуля.
- ALS содержит ровно один управляющий модуль (`LC` или `LBC`) и не менее одного модуля хранения (`LB` или `LBC`).
- LC и LBC не могут одновременно присутствовать в одной ALS.
- Допустимые базовые композиции: `LC + LB`, `LB + LC`, `LB + LC + LB`, `LBC`, `LBC + LB`, `LB + LBC`, `LB + LBC + LB`.
- Физический порядок модулей — упорядоченный список слева направо. Он является единственным источником истины для расположения модулей. Положение управляющего модуля и направления дверей вычисляются из этого списка.
- Порядок модулей влияет на идентичность ALS; перестановка модулей означает другую конфигурацию.
- Положение и правила добавления одинаковы для LC и LBC:
  - LEFT: управляющий модуль находится слева, LB располагаются справа от него;
  - CENTER: LB располагаются по обе стороны управляющего модуля;
  - RIGHT: LB располагаются слева от управляющего модуля.
- При последовательном добавлении LB в положении LEFT новый LB располагается справа от управляющего модуля; в положении RIGHT — слева от управляющего модуля. При CENTER новые LB распределяются по обе стороны управляющего модуля так, чтобы разница между количеством LB слева и справа не превышала одного. Новый LB добавляется на сторону, где LB меньше; если количество одинаково, допустима любая сторона.
- Добавление LB выполняется как бизнес-операция ALS с соблюдением положения управляющего модуля; произвольная вставка по индексу не должна подменять это правило.
- Для ALS, состоящей только из одного LBC, в техническом представлении допускается значение CENTER как нейтральное значение по умолчанию. Оно не означает физическое центральное положение и не должно показываться пользователю как отдельная физическая позиция.

### 10.3. Направления дверей

Направления вычисляются при пересчёте ALS на основании фактического физического порядка модулей:

- обычный LB слева от управляющего LC/LBC открывается влево (`LEFT`);
- обычный LB справа от управляющего LC/LBC открывается вправо (`RIGHT`);
- для самого LBC применяется отдельное правило:
  - управляющий модуль в положении LEFT → направление дверей LBC RIGHT;
  - положение CENTER → LEFT;
  - положение RIGHT → LEFT.
- Для одиночного LBC применяется нейтральное техническое значение CENTER; следовательно, направление его дверей — LEFT.
- Направления не задаются независимо от положения модулей и пересчитываются при изменении состава или порядка ALS.

### 10.4. Оборудование и функциональность

- Фактически установленное оборудование хранится в `EquipmentConfiguration` внутри управляющей части LC/LBC. Оборудование не является отдельным модулем ALS.
- `FunctionalSelection` — временное состояние выбора пользователя в конфигураторе. Оно не является самостоятельной сохраняемой доменной сущностью.
- Выбор функциональности включает способы доступа и вариант оплаты. Самостоятельный выбор `PrintOption` не используется: необходимость принтера определяется выбранными способами доступа и/или оплатой.
- Выбранные способы доступа и вариант оплаты относятся к конфигурации управления; конкретные модели устройств и их количество сохраняются в `EquipmentConfiguration`.
- Для LC и LBC применяется единый целевой механизм разрешения требований к оборудованию — `EquipmentRequirementResolver`.
- Система автоматически подбирает совместимое оборудование по умолчанию и сразу показывает пользователю получившуюся комплектацию при выборе или изменении функциональности. Подбор не откладывается до сохранения конфигурации.
- Пользователь может заменить предложенную модель на другую активную и совместимую модель.
- При изменении функциональности система немедленно пересчитывает комплектацию: сохраняет оборудование, которое требуется оставшимся функциям, удаляет оборудование, которое больше не требуется, и добавляет недостающее. Отдельного признака ручного закрепления оборудования нет.
- Один компонент оборудования может обеспечивать несколько функций. В этом случае физически он включается в комплектацию один раз и учитывается всеми функциями, которые он обеспечивает.
- Наличие принтера не выбирается независимо: принтер обязателен при ненулевой оплате либо при выборе BARCODE, QR или PIN. При отсутствии этих требований система не добавляет принтер автоматически.
- RFID требует RFID-считыватель; BARCODE — считыватель штрихкодов; QR — QR-считыватель. PIN требует дисплей диагональю 10, 17 или 19 дюймов и как минимум один дополнительный способ доступа из RFID, BARCODE или QR; PIN не может быть единственным способом доступа.
- Для оплаты безналичным способом требуется банковский терминал; для наличной оплаты — оборудование приёма наличных; при обоих способах требуются оба вида оборудования.
- Дисплей в LC/LBC — ровно один. Выбор ограничен диагоналями 10, 17 или 19 дюймов; разные каталожные модели с разными ID являются разными позициями оборудования.
- Идентичность позиции оборудования в составе конфигурации определяется ID каталожной позиции; количество хранится отдельно. Порядок записей оборудования не имеет предметного значения. Для дисплея количество всегда равно единице.
- Для каждого требования/категории каталога допускается ровно одна активная модель по умолчанию. Каталог должен обеспечивать совместимую модель по умолчанию для каждой доступной функции; несовместимую или неполную комплектацию сохранять нельзя.
- Деактивированная модель остаётся в ранее сохранённых конфигурациях. При редактировании такой конфигурации её можно оставить без изменений, но нельзя повторно выбрать или добавить; для новых конфигураций она недоступна.
- Если для доступной пользователю функции нет совместимой модели, это нарушение целостности каталога/настроек системы, а не штатная пользовательская ошибка.
- Доменная модель не обращается к репозиториям и инфраструктуре. Подбор каталожных моделей и координация требований выполняются на прикладном уровне через соответствующий resolver; доменные объекты проверяют переданные конфигурации и инварианты.

### 10.4.1. Матрица функциональности и отображение комплектации

| Выбор пользователя | Требуемое оборудование / ограничение |
|---|---|
| RFID | RFID-считыватель |
| BARCODE | Считыватель штрихкодов |
| QR | QR-считыватель |
| PIN | Дисплей 10″, 17″ или 19″ и минимум один дополнительный способ доступа: RFID, BARCODE или QR |
| Наличная оплата | Оборудование приёма наличных |
| Безналичная оплата | Банковский терминал |
| Наличная и безналичная оплата | Оборудование приёма наличных и банковский терминал |
| Любая ненулевая оплата | Принтер обязателен |
| BARCODE, QR или PIN | Принтер обязателен |
| Только RFID без оплаты | Принтер не требуется автоматически |

При выборе или изменении функциональности пользователь сразу видит фактически подобранные модели оборудования. Если один компонент нужен нескольким функциям, он показывается и устанавливается один раз. Принтер не является самостоятельным переключателем функциональности: его необходимость выводится из выбранных способов доступа и оплаты.

### 10.5. Идентичность и жизненный цикл конфигураций

- Сохранённые конфигурации оборудования, модулей и ALS неизменяемы по бизнес-полям.
- Изменение сохранённой конфигурации выполняется через Find-or-Create: найти полностью эквивалентную конфигурацию либо создать новую; затем заменить ссылку в проекте.
- Идентичность ALS включает все значимые входные характеристики и полный упорядоченный состав модулей.
- Идентичность модуля включает его тип и значимые входные параметры, а также состав оборудования.
- Идентичность оборудования в составе конфигурации определяется конкретной каталожной позицией по ID; количество — отдельный атрибут связи. Порядок оборудования не влияет на идентичность комплектации.
- Названия, описания, рассчитанные размеры ячеек, нумерация ячеек и прочие производные характеристики не участвуют в идентичности.
- Целевой жизненный цикл конфигурации: DRAFT → SAVED/IMMUTABLE → USED → ORPHAN. Архивация — отдельная административная операция, не равная физическому удалению.
- Используемые конфигурации нельзя физически удалять. Неиспользуемые конфигурации могут переводиться в архив по установленной административной процедуре.

### 10.6. Геометрия и общие параметры ALS

- Высота, глубина, верхняя/нижняя рамы и цвета корпуса/дверей являются общими параметрами ALS и синхронизируются со всеми её модулями.
- Ширина ALS равна сумме ширин всех модулей в физическом порядке.
- Формулы расчёта:
  - ширина ячейки = ширина модуля − `deltaWidth` − `serviceZoneWidth`;
  - глубина ячейки = глубина модуля − толщина дверцы;
  - полезная высота = высота модуля − верхняя рама − нижняя рама − (`countCells - 1`) × толщина полки;
  - высота ячейки = полезная высота / количество ячеек.
- Дробная часть высоты ячейки отбрасывается вниз; математическое округление не применяется.
- Максимум 20 ячеек — абсолютное ограничение. Фактически допустимое количество определяется также условием минимальной высоты ячейки 85 мм и толщиной полки.
- При смене типа LB/LBC обновляются связанные параметры типа (`deltaWidth`, `shelfThick`, `serviceZoneWidth`), после чего выполняются перерасчёт и полная валидация. Если конфигурация становится недопустимой, изменение отклоняется с перечислением нарушений.
- Толщина дверцы настраивается отдельно для LB/LBC, влияет на глубину ячейки и проходит валидацию.
- Все размеры задаются в миллиметрах. Числовые границы и defaults фиксируются в `size-bounds.properties` и сводном разделе бизнес-логики.

### 10.7. Валидация

- Валидация должна проверять структуру ALS, ограничения каждого модуля, геометрические формулы, совместимость оборудования и ограничения всего проекта.
- Проверка не должна останавливаться на первой ошибке: возвращается полный набор обнаруженных нарушений.
- Каждая ошибка должна позволять определить объект и конкретный модуль, параметр, фактическое значение и допустимое ограничение/условие.
- Для модулей без persistence ID ошибка всё равно должна однозначно указывать на модуль в составе ALS (например, через позицию/путь в составе).
- Нельзя сохранять конфигурацию, нарушающую структурные инварианты, геометрические ограничения или совместимость/полноту оборудования.

### 10.8. Формирование названий и описаний

Названия и описания — производные представления конфигураций и не участвуют в идентичности.

- LB: имя `Модуль хранения на {countCells} ячеек`. Описание включает количество ячеек, тип, размеры ячейки (В×Ш×Г), габариты (В×Ш×Г), направление дверей, цвета и толщину дверцы.
- LC: имя `Модуль управления {displayName}` либо «Без дисплея». Описание включает дисплей, габариты, рамы, способы доступа, варианты печати, оплату, установленное оборудование и цвета.
- LBC: имя `Комбинированный модуль на {countCells} ячеек`. Описание включает параметры хранения (тип, количество и размеры ячеек, габариты, направление дверей, цвета, толщину дверцы) и параметры управления (дисплей, способы доступа, печать, оплату, установленное оборудование).
- ALS: имя `АКХ на {totalCells} ячеек`. Описание отражает общее количество ячеек, габариты, цвета, количество и состав модулей с сохранением их физического порядка, а также параметры управляющего модуля.
- Project: название задаётся пользователем; описание автоматически формируется по полному составу проекта и количеству каждой конфигурации ALS.
- Изменение шаблонов названий/описаний не должно менять идентичность конфигурации.

### 10.9. Сотрудники и разграничение доступа

- `Employee` — доменная модель сотрудника. Пароль/хэш пароля, JWT и security principal не относятся к доменному объекту.
- Отдельная доменная сущность `UserAccount` не вводится. Текущая `EmployeeEntity` может хранить данные сотрудника и учётные данные на persistence/security-уровне.
- Менеджер видит все проекты, но может изменять только проекты, владельцем которых является он сам.
- Администратор может изменять любые проекты.
- Удаление сотрудника не должно физически удалять или обесценивать проекты и историю авторства. Сотрудник деактивируется; деактивация блокирует авторизацию, сохраняя ссылки на автора/редактора.
- Статус активности относится к persistence/security-слою и не требует введения отдельного доменного `UserAccount`.

### 10.10. Гостевой режим и импорт проектов

- Гостевые проекты хранятся в IndexedDB браузера; до импорта серверная БД их не содержит.
- Гостевой режим использует те же доменные правила расчёта и валидации.
- После регистрации/входа пользователь выбирает проекты для импорта. Сервер повторно валидирует данные и назначает владельца по аутентифицированному principal.
- Для каждого гостевого проекта используется постоянный `guestProjectId` как ключ идемпотентности.
- Повторная отправка того же `guestProjectId` возвращает результат первоначального импорта и не создаёт второй проект.
- Разные `guestProjectId` не считаются дубликатами только на основании совпадения названия. При обнаружении похожего проекта система может предупредить пользователя, но не должна автоматически перезаписывать существующий проект.
- Локальная копия удаляется только после подтверждения успешного сохранения на сервере. При ошибке или неопределённом результате она сохраняется и может быть отправлена повторно.
- Сервер не доверяет переданному клиентом owner ID; владельцем становится текущий аутентифицированный сотрудник.

### 10.11. Порядок полного пересчёта ALS

Полный пересчёт ALS выполняется в следующей последовательности:

1. Проверка структурных инвариантов.
2. Синхронизация общих параметров ALS с модулями.
3. Определение положения управляющего модуля по упорядоченному списку.
4. Расчёт направлений дверей обычных LB и LBC.
5. Пересчёт геометрии каждого модуля и ячеек.
6. Проверка нумерации и последовательное назначение номеров ячеек слева направо.
7. Расчёт общей ширины ALS.
8. Формирование названий и описаний модулей и ALS.

### 10.12. Вопросы, отложенные за рамки текущего этапа

Незакрытых вопросов доменной модели, необходимых для текущего этапа проектирования, нет.

Физическое оборудование хранения и замков (`ELECTRONIC_LOCK`, `LOCK_CONTROLLER`) отложено как отдельная будущая доработка. Эти компоненты не входят в текущую доменную модель и согласованную комплектацию LB/LBC. Необходимость компонентов, количество замков и правила распределения контроллеров по физическим модулям будут определены отдельно.

Правила распределения LB при CENTER, матрица требований функций и оборудования, отсутствие признака ручного закрепления оборудования, уникальность активной default-модели и политика деактивации каталожных позиций согласованы.
